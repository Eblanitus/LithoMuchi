## 1. Коротко

**Что делаем.** Мод, который заменяет «случайные» слои ванильной генерации (где вода, где суша, какой климат) на правдоподобную модель: сначала случайно, но в рамках правдоподобия раскладываются литосферные плиты, из плит выводятся материки, горы, океанические желоба и хребты, реки и влажность. Температура задаётся отдельно: «полюсами-точками» на плоской карте, от которых расходятся климатические пояса. Мир бесконечный и статичный. Биомы и блоки только ванильные.

**Где работает.** Horizon: Minecraft Java 26.3, переписанный на Rust, со встроенным загрузчиком модов. Мод пишется на Rust.

**Ключевая архитектурная идея** [ПРЕДЛОЖЕНИЕ]. Вся наука живёт в отдельной библиотеке `litho-core` без зависимостей от игры. Она по координатам `(x, z)` и сиду считает пять «климатических параметров» ванили: континентальность, эрозию, «странность» (weirdness), температуру и влажность. Ванильный генератор Horizon уже умеет строить из этих пяти чисел рельеф, выбирать биомы, пещеры, аквиферы и дальний LOD. Мы подменяем только источник этих чисел. Для этого хватает **одной точки внедрения в код Horizon** и одного датапака на каждый режим. Лава на глубине −54 привязывается к стыкам плит ещё одной точкой внедрения и полем датапака.

**Первая веха** [РЕШЕНО]. Не мод, а **песочница**: библиотека генерации плюс программа, которая рисует карту мира сверху (плиты, пояса, температура, влажность, биомы). По картинкам автор оценивает, красиво и правдоподобно ли. Мод в Horizon идёт после этого. Параллельно с песочницей можно вести короткую разведку Horizon (раздел 13, этап 2), она не мешает первой вехе.

## 2. Цели и не-цели

### 2.1. Цели

| # | Цель | Статус |
|---|---|---|
| Ц1 | Работающий мод генерации мира: создаёшь мир в Horizon, видишь горы на стыках плит, климатические пояса от полюсов, правдоподобные биомы. «Работает» значит, что мир генерируется в самой игре. | [РЕШЕНО] |
| Ц2 | Бесконечный мир. Никаких «карт фиксированного размера». | [РЕШЕНО] |
| Ц3 | Основной слой: случайные литосферные плиты, «как мы их знаем сейчас», случайность в рамках правдоподобия. От плит выводятся горы, реки, биомы, влажность. | [РЕШЕНО] |
| Ц4 | Температура не от литосферы, а от положения относительно «солнца»: полюса-точки, от них пояса, которые сливаются в широкие экваториальные зоны. | [РЕШЕНО] |
| Ц5 | Влажность «по-умному»: пояс плюс дождевая тень (постоянный ветер в поясе) плюс то, откуда дует ветер (с океана или с материка). | [РЕШЕНО] |
| Ц6 | Два режима: геймплейный (как ванильная генерация, уменьшенная версия научного) и научный (максимально правдоподобно, менее играбельно, например по 1000 блоков одного биома). Выбор режима в меню при создании мира. | [РЕШЕНО] |
| Ц7 | Лавовые озёра на глубине около −50 (в ванили там «просто много лавы где попало») привязать к стыкам плит. | [РЕШЕНО], как минимальное изменение подземелья |
| Ц8 | Открытый исходный код. | [РЕШЕНО] |
| Ц9 | Платформа Horizon, версия Horizon фиксируется. Запасной вариант: та же Rust-библиотека под Fabric. | [РЕШЕНО] |

### 2.2. Не-цели (сознательно не делаем)

| # | Не делаем | Статус |
|---|---|---|
| Н1 | Никакого движения и времени: нет дрейфа плит, сезонов, смены уровня моря, истории геологии. Мир статичен. | [РЕШЕНО] |
| Н2 | Не трогаем пещеры (кроме лавы на −54, см. Ц7). | [РЕШЕНО] |
| Н3 | Не добавляем свои блоки. Биомы только ванильные. Свои биомы из ванильных блоков, например очень глубокие океаны, возможно позже, «если будет легко» (см. 7.13: сейчас это не легко). | [РЕШЕНО] |
| Н4 | Не делаем мод на Java. Ядро на Rust принципиально. | [РЕШЕНО] |
| Н5 | Ветер не игровая механика. Он нужен только внутри модели влажности. | [РЕШЕНО] |
| Н6 | Совместимость с существующими мирами и другими модами пока не цель. | [РЕШЕНО] |
| Н7 | Не симулируем реальную тектонику и эрозию во времени. Делаем правдоподобную статичную «подделку», которую можно считать локально (см. 6.5). | [ПРЕДЛОЖЕНИЕ], следует из Ц2 и Н1 |
| Н8 | Не меняем движок Horizon вне генерации и не просим автора Horizon о новом API сейчас. Официальный хук генерации в Horizon возможен «на далёкое будущее». | [РЕШЕНО] (PR-хук «не сейчас») |

### 2.3. Принципы реализации [ПРЕДЛОЖЕНИЕ]

1. **Детерминизм.** Один и тот же сид, режим и версия генератора дают побитово одинаковый результат на любой машине, в любом порядке генерации, в любом числе потоков.
2. **Локальность.** Значение в точке считается по ограниченной окрестности точки. Никаких проходов «по всему миру».
3. **Ядро без зависимостей.** `litho-core` использует только стандартную библиотеку Rust. Причина техническая: нативный мод Horizon может брать только те внешние крейты, что уже есть в `Cargo.lock` Horizon (раздел 5.4).
4. **Тонкая интеграция.** Код, который вставляется в Horizon, делает минимум: переводит вызовы движка в вызовы ядра. Всё остальное тестируется без игры.
5. **Сначала картинка, потом игра.** Любое изменение алгоритма сначала смотрится в песочнице.
6. **Версия генератора неизменна.** Выпущенная версия генератора никогда не меняет вывод. Любое изменение формул это новая версия (раздел 6.8), иначе у игроков появятся швы между старыми и новыми чанками.

## 3. Глоссарий

Термины геологии, климатологии, Minecraft и Horizon в том смысле, в каком они используются в этом плане.

### 3.1. Геология

| Термин | Значение |
|---|---|
| **Литосфера** | Жёсткая внешняя оболочка планеты (кора плюс верх мантии). Разбита на плиты. |
| **Литосферная плита (плита)** | Крупный жёсткий кусок литосферы, который движется как целое. У нас: область карты с общими свойствами (тип коры, скорость). Плиты не движутся во времени, скорость нужна только чтобы решить, что происходит на границе. |
| **Граница плит (стык, шов)** | Линия, где встречаются две плиты. Тип границы определяется относительным движением. |
| **Конвергентная граница** | Плиты сходятся. Даёт горы (столкновение материков: Гималаи), глубоководный жёлоб и вулканическую дугу (субдукция: Анды, Япония). |
| **Дивергентная граница** | Плиты расходятся. В океане это срединно-океанический хребет, на материке рифт (Восточно-Африканский рифт, Красное море). |
| **Трансформная граница** | Плиты скользят вдоль границы (разлом Сан-Андреас). Рельеф слабый: уступы, вытянутые долины. |
| **Субдукция** | Погружение более тяжёлой (океанической) плиты под другую. Над ней жёлоб и цепь вулканов. |
| **Островная дуга** | Цепь вулканических островов над зоной субдукции океан–океан (Алеуты, Марианы). |
| **Срединно-океанический хребет (СОХ)** | Подводный хребет на расходящейся океанической границе. Поднимается над абиссальной равниной, но остаётся под водой. |
| **Рифт** | Провал на расходящейся континентальной границе: узкая долина с плечами, озёра, иногда молодое море. |
| **Горячая точка** | Место подъёма мантийного вещества внутри плиты. Даёт вулканические острова (Гавайи) или плато (Йеллоустоун). |
| **Тройное сочленение** | Точка, где сходятся три плиты. |
| **Континентальная кора / океаническая кора** | Лёгкая толстая кора материков (средняя высота около +0,8 км) и тяжёлая тонкая кора океанов (около −4 км). |
| **Шельф, континентальный склон** | Мелководная окраина материка (до −0,2 км) и крутой спуск с неё к абиссали. |
| **Абиссальная равнина** | Плоское дно океана на глубине 4–5 км. |
| **Пассивная окраина** | Побережье, которое не совпадает с границей плит (Атлантика). Материк и океан на одной плите. |
| **Активная окраина** | Побережье на границе плит (тихоокеанское побережье Южной Америки). |

### 3.2. Климат

| Термин | Значение |
|---|---|
| **Полюс-точка** | Наша замена полюса планеты на плоской бесконечной карте: точка, вокруг которой холодно. Полюсов бесконечно много, все «северные». [РЕШЕНО] |
| **Псевдоширота φ** | Число от 0° до 90°, которое заменяет географическую широту: 90° на полюсе-точке, 0° на «экваторе» (линии, равноудалённой от двух ближайших полюсов). |
| **Климатический пояс** | Полоса псевдошироты с похожим климатом: экваториальный, тропический, субтропический, умеренный, субполярный, полярный. |
| **Экватор** | У нас: множество точек, где расстояния до двух ближайших полюсов равны. Получается сеть широких экваториальных зон между «территориями» полюсов. |
| **Пассаты** | Постоянные ветры от 0° до 30° широты, дуют к экватору и на запад. |
| **Западные ветры** | Постоянные ветры от 30° до 60°, дуют к полюсу и на восток. |
| **Полярные восточные ветры** | Ветры выше 60°, дуют от полюса и на запад. |
| **Штилевая зона (ITCZ)** | Зона у экватора, где пассаты сходятся. Ветер слабый, дожди сильные. |
| **Дождевая тень** | Сухая область за горным хребтом по ветру: влажный воздух теряет воду на наветренном склоне. |
| **Орографические осадки** | Дополнительные осадки на наветренном склоне, когда воздух поднимается в гору. |
| **Вертикальный температурный градиент** | Падение температуры с высотой, в среднем 6,5 °C на километр. |
| **Испаряемость (PET)** | Сколько воды могло бы испариться при данной температуре, мм в год. |
| **Индекс сухости (отношение PET/P)** | Испаряемость, делённая на осадки. Больше 1: сухо, меньше 1: влажно. |
| **Биотемпература** | Средняя температура за год, где месяцы ниже 0 °C считаются как 0 °C (и выше 30 °C как 30 °C). Нужна для схемы Холдриджа. |
| **Жизненные зоны Холдриджа** | Научная классификация растительности по биотемпературе, осадкам и индексу сухости. Основа нашей классификации биомов (7.8). |
| **Континентальность** | Насколько далеко место от смягчающего влияния океана. Влияет на размах температур по сезонам. |

### 3.3. Процедурная генерация

| Термин | Значение |
|---|---|
| **Сид** | Число, из которого детерминированно выводится весь мир. В Minecraft знаковое 64-битное. |
| **Хэш** | Функция, которая превращает набор целых чисел (сид, номер ячейки) в «случайное» 64-битное число. Одинаковый вход всегда даёт одинаковый выход. Так мы получаем случайность без хранения состояния. |
| **Детерминизм** | Свойство: результат зависит только от входа (сид, координаты, режим, версия), а не от порядка вычислений, числа потоков или машины. |
| **Локальность** | Свойство: значение в точке зависит только от ограниченной окрестности. Это то, что делает возможным бесконечный мир. |
| **Джиттер-сетка** | Способ разбросать точки: делим плоскость на квадратные ячейки и в каждой ставим точку в случайном (по хэшу) месте. |
| **Ячейка Вороного** | Множество точек плоскости, для которых данная точка-семя ближайшая. Набор ячеек Вороного называется диаграммой Вороного. |
| **F1, F2** | Расстояния от точки до ближайшего и второго по близости семени. |
| **Градиентный шум (шум Перлина, симплекс-шум)** | Гладкая псевдослучайная функция плоскости со значениями около [−1, 1]. Основа почти всей процедурной генерации. |
| **Октава, fBm** | fBm (fractional Brownian motion) это сумма нескольких копий шума («октав»), каждая следующая в 2 раза мельче и примерно в 2 раза слабее. Даёт детали на многих масштабах. |
| **Искажение домена (domain warp)** | Сдвиг координат шумом перед вычислением функции. Делает прямые границы волнистыми. |
| **Решётка, интерполяция** | Дорогую функцию считаем только в узлах регулярной сетки, а между ними восстанавливаем гладкой интерполяцией (бикубической). |
| **Макро-единица L** | Наша единица длины для крупных структур: сколько блоков в одной «условной сотне километров». Разная в двух режимах (раздел 8). |

### 3.4. Minecraft (ванильная генерация 1.18+)

| Термин | Значение |
|---|---|
| **Блок, чанк** | Блок: кубик 1×1×1. Чанк: колонна 16×16 блоков по горизонтали на всю высоту мира. |
| **Quart (четвертинка)** | Ячейка 4×4×4 блока. Биомы в Minecraft хранятся с таким разрешением. |
| **Высота мира** | Ванильный Верхний мир: Y от −64 до 319. Уровень моря 63. |
| **Density function (функция плотности)** | Функция `(x, y, z) → число`. Положительная: камень, отрицательная: воздух или вода. Ванильный рельеф целиком собран из таких функций, описанных в JSON. |
| **Noise router (маршрутизатор шумов)** | Набор именованных функций плотности, которые генератор использует для рельефа и климата. В 26.3 у него 8 полей (раздел 5.3). |
| **Климатические параметры** | Шесть чисел, по которым ваниль выбирает биом: температура (T), влажность (H, в коде vegetation), континентальность (C), эрозия (E), странность (W, в коде ridges/weirdness) и глубина (D). C, E и W одновременно управляют высотой рельефа. |
| **PV (peaks and valleys)** | Производная от W величина: `PV = 1 − \|3\|W\| − 2\|`. PV = −1 это долина (там ваниль делает реки), PV = 1 это гребень. |
| **Multi-noise biome source** | Ванильный выбор биома: в таблице из нескольких тысяч «точек» ищется ближайшая к шести параметрам в данной точке. |
| **Аквифер** | Подземная система воды и лавы в ванили 1.18+. Решает, где в пещерах вода, где лава, где воздух. |
| **Fluid picker** | Глобальное правило «какая жидкость на этой высоте». В ванили: ниже Y = −54 лава, ниже уровня моря вода. Отсюда «много лавы на −50». |
| **Датапак (data pack)** | Папка или zip с JSON-данными, которые заменяют или добавляют данные игры, включая генерацию мира. Включается для конкретного мира. |
| **Пресет мира (тип мира)** | «Обычный», «Плоский», «Большие биомы», «Расширенный» и т. п. на экране создания мира. |

## 5. Платформа Horizon: что известно

Всё в этом разделе проверено на коммите `f319701` (ночная сборка 2026-11-05), если не сказано иное.

### 5.1. Общее

- Horizon это Minecraft Java Edition 26.3, целиком переписанный на Rust: клиент, сервер и лаунчер. Лицензия MIT. Автор Ludovic Marie. Сайт `playhorizon.dev`. [ПРОВЕРЕНО: README]
- Нужна своя копия Java Edition 26.3 (Microsoft-аккаунт с игрой). Horizon не содержит кода и ресурсов Mojang, а готовит их из вашей копии. [ПРОВЕРЕНО: README]
- Ванильная генерация мира воспроизведена: «2 352 чанка целиком, идентичны ванили» по их собственным сравнительным тестам. [ПРОВЕРЕНО: README, docs/world-generation.md]
- Датапаки, в том числе с генерацией мира, работают. Формат датапаков 26.3 отличается от 26.2 и тем более от 1.21: функции плотности берут `left`/`right`, `gradient` заменил `y_clamped_gradient`, шумы берут `base_octave`/`octave_count`, состояния блоков стали строками, правила поверхности переехали в реестры `material_rule` и `material_condition`. [ПРОВЕРЕНО: docs/world-generation.md]
- Java-моды (Fabric, NeoForge) не работают. Есть свои content-моды (данные) и нативные моды (Rust). [ПРОВЕРЕНО: docs/mods.md]
- Дальний рельеф (LOD) до 1024 чанков и дальше. **Неизвестные области LOD сэмплирует напрямую из функций плотности и правил поверхности генератора**, значит наши поля будут видны в LOD, и они же будут нагружены вычислениями LOD. [ПРОВЕРЕНО: docs/graphics.md, раздел Distant terrain]
- Проект молодой (с октября 2026), код в основном написан с помощью ИИ, коммитов очень много. Это главный источник риска (раздел 16).

### 5.2. Моды

- **Content mod (`.hmod`)**: данные и ресурсы, без кода. Файлы только в своём пространстве имён (`data/<id>/`, `assets/<id>/`) плюс дополнения к ванильным тегам. **Ванильные файлы генерации `data/minecraft/worldgen/...` content-мод заменить не может.** [ПРОВЕРЕНО: docs/mods.md, раздел Namespaces and limits]
- **Native mod (`.hnmod`)**: бандл `horizon-mixins`. Лаунчер скачивает исходники закреплённого коммита Horizon, применяет миксины всех включённых модов и компилирует игру. Код модов не изолирован (работает с правами игрока), поэтому лаунчер требует явного доверия. [ПРОВЕРЕНО: docs/native-mods.md]
- Нативный мод закрепляется на точном коммите: `[compatibility] horizon_revision` в `horizon-mixin.toml`. Ночные сборки хранятся навсегда под тегом `nightly-source/<дата>-<коммит>`. Если моды одной сборки закреплены на разных коммитах, лаунчер предлагает «Build anyway». Мод, который не применился (`E_TARGET_NOT_FOUND` и т. п.), исключается из сборки с объяснением. [ПРОВЕРЕНО: docs/native-mods.md, раздел Pinned to a Nightly]
- Публикация: публичный репозиторий на GitHub с лицензией, разрешающей игрокам запуск; GitHub release с файлом `.hnmod`; один раз заявка на `playhorizon.dev/mods/submit` (ревью человеком), дальше релизы проверяются автоматически. [ПРОВЕРЕНО: docs/mods.md, раздел Publish your mod]

### 5.3. Генерация мира в Horizon 26.3

- Маршрутизатор шумов (`horizon_world::worldgen::router::RouterField`) имеет **8 полей**: `temperature`, `vegetation`, `continents`, `erosion`, `depth`, `ridges`, `chunk_surface_level`, `final_density`. Первые шесть это климатические параметры. [ПРОВЕРЕНО: crates/horizon-world/src/worldgen/router.rs]
- В настройках шума 26.3 эти поля это **ссылки на именованные функции плотности** `minecraft:overworld/temperature`, `…/vegetation`, `…/continents`, `…/erosion`, `…/ridges`, `…/depth`. Значит, чтобы подменить поле, достаточно переопределить маленький файл функции плотности, а не весь `noise_settings/overworld.json`. [ПРОВЕРЕНО по фикстуре Horizon `tools/fixtures/datapacks/horizon_worldgen_test/data/minecraft/worldgen/noise_settings/overworld.json`; что ванильные файлы 26.3 устроены так же, проверяет T71]
- Формат функций плотности 26.3 (декодер `crates/horizon-world/src/worldgen/density.rs`): узел `minecraft:noise` с полями `noise` (только ссылка на шум), `xz_scale`, `y_scale` и необязательными `shift_x/y/z`; кэш одного типа `minecraft:cache` с полем `input`; бинарные узлы с `left`/`right`. Определение шума: `base_amplitude`, `base_octave`, `octave_count`. [ПРОВЕРЕНО]
- Узел шума без сдвигов вызывает `noise.get3(x·xz_scale, y·y_scale, z·xz_scale)` от целых координат запроса, а для объёмов `noise.add_to_volume(буфер, объём, xz_scale, y_scale, 1.0)`. Реализация `add_to_volume` по умолчанию зовёт `get3` для каждой точки объёма. Значения шума `f32`. [ПРОВЕРЕНО: crates/horizon-core/src/density/mod.rs, noise/stack.rs]
- Настройки аквиферов отдельно (`AquiferField`): `barrier`, `fluid_level_floodedness`, `fluid_level_spread`, `lava`, `exclusion`, `surface_level`. Они читаются из объекта `aquifers` внутри настроек шума; каждое поле это функция плотности (ссылкой или встроенная). [ПРОВЕРЕНО: crates/horizon-world/src/worldgen/aquifer/config.rs, generator.rs]
- Скомпилированные функции плотности это объекты-трейты `Arc<dyn DensitySampler>` (крейт `horizon-core`). Узел графа `GraphNode::Noise` ссылается на шум по `NoiseId`. [ПРОВЕРЕНО: crates/horizon-core/src/density/graph/mod.rs, density/mod.rs]
- **Экземпляр шума создаётся функцией `SeededContext::noise(graph, id)`** (файл `crates/horizon-core/src/density/graph/seeded.rs`). Она знает имя шума (`entry.name`) и уже содержит особый случай по имени (`minecraft:nether/temperature`). Возвращает `Result<Arc<dyn Noise>, CompileError>`. Это наша главная точка внедрения (10.1). [ПРОВЕРЕНО]
- Трейт `horizon_core::noise::Noise` (файл `crates/horizon-core/src/noise/stack.rs`): методы `range()`, `get2(x, z)`, `get3(x, y, z)` и `add_to_volume(...)` с реализацией по умолчанию. [ПРОВЕРЕНО]
- **Диапазон значений узла шума граф берёт из JSON-определения шума, а не из экземпляра** (`self.noise_entry(noise)?.definition.range()` в `graph/mod.rs`). Если наш экземпляр выдаёт значения шире объявленного диапазона, оптимизации компилятора (выбор ветки по интервалу, отсечение констант) могут дать неверный рельеф. Фиктивное определение шума в датапаке обязано объявлять диапазон не уже наших значений. [ПРОВЕРЕНО: чтение кода; последствия нарушения НЕ ПРОВЕРЕНЫ запуском]
- Глобальный выбор жидкости: `GlobalFluidPicker::compute` (`crates/horizon-world/src/worldgen/aquifer.rs`): **лава при `y < min(−54, sea_level)`**, иначе вода до уровня моря. Структура хранит только уровень моря и id блоков, конструктор `new` это `const fn`, создаётся он внутри `Pipeline<R>::new` (обобщённый `impl`). [ПРОВЕРЕНО]
- Лава в аквиферах: если уровень жидкости ячейки `≤ −10` и `|lava(x div 64, y div 40, z div 64)| > 0.3`, то лава (`aquifer/noise_based.rs`). Поле `lava` вызывается **в координатах ячеек 64×40×64**, а не блоков. [ПРОВЕРЕНО]
- Поиск точки появления (`spawn_finder.rs`): перебор вокруг 0,0 в радиусе **2048 блоков** по «целевым» климатическим точкам `spawn_target` из настроек шума. [ПРОВЕРЕНО]
- Высоту мира датапак может поднять через тип измерения: верх не выше 2032, кратно 16. [ПРОВЕРЕНО: docs/world-height.md]
- Новые биомы из датапаков Horizon отбрасывает («у игры нет для них id, цветов и звуков»). [ПРОВЕРЕНО: docs/world-generation.md, раздел Data packs]
- Таблицу выбора биомов Верхнего мира Horizon не строит кодом, а берёт из отчёта генератора данных `biome_parameters/<имя>.json` (или квантованного `presets.json`) в подготовленных данных игры. Значит, точную таблицу 26.3 можно прочитать из той же копии игры. [ПРОВЕРЕНО: generator.rs, biome_source/runtime.rs]
- Пресеты мира (`world_preset`) из датапаков Horizon **не читает**. Тип мира на экране создания это закрытый Rust-enum `WorldPreset` с пятью вариантами (Normal, Flat, LargeBiomes, Amplified, SingleBiomeSurface). Добавить туда свой пункт без структурной правки кода нельзя. [ПРОВЕРЕНО: horizon-client/src/save.rs, horizon-world/src/worldgen/overrides.rs]
- На экране создания мира есть вкладки Game, World, More и экран Data Packs. Встроенные «feature»-паки берутся из папки `<resources>/data/minecraft/datapacks/`, пользовательские из временной папки. [ПРОВЕРЕНО: horizon-client/src/title/create_world.rs, horizon-client-render/src/datapack.rs]

### 5.4. Ограничения на код нативного мода

- Свой крейт бандла (`[[crate]]`) может брать **только внешние крейты, которые уже есть в `Cargo.lock` Horizon**, в подходящей версии. Нельзя path- и git-зависимости, нельзя свой `Cargo.lock`, `[workspace]` и сборку своего build-скрипта. Нельзя зависеть от крейтов Horizon (это path-крейты). [ПРОВЕРЕНО: docs/native-mods.md, раздел The mod's crate]
- Что есть в `Cargo.lock` Horizon на `f319701` (выборочно): `serde 1.0.229`, `serde_json 1.0.151`, `toml 1.1.6`, `glam 0.30.10`, `libm 0.2.16`, `rustc-hash 1.1.0`, `ahash 0.8.12`, `parking_lot 0.12.5`, `smallvec 1.16.2`, `png 0.18.1`, `rand 0.10.3`. **Нет**: `rayon`, `image`, `noise`, `fastnoise-lite`. [ПРОВЕРЕНО]
- Workspace Horizon: `edition = "2024"`, `rust-version = "1.85"`. [ПРОВЕРЕНО: Cargo.toml]
- Крейт бандла копируется в workspace Horizon, поэтому в его `Cargo.toml` **нельзя** использовать наследование `version.workspace = true` и т. п.: оно разрешится относительно workspace Horizon. [ПРЕДЛОЖЕНИЕ, вывод из механики staging]
- Поле `dependent` у `[[crate]]` указывает, какой пакет workspace Horizon зависит от нашего крейта (по умолчанию `horizon-client`). Можно указать любой член workspace, например `horizon-core`. [ПРОВЕРЕНО: horizon-mixins docs/crates-data-and-named-hooks.md]
- Код вспомогательных модулей (`[[module]]`) не может содержать внутренних атрибутов файла (в том числе комментариев `//!`), внешних `mod`-файлов и `include!`. [ПРОВЕРЕНО: README шаблона нативного мода]

### 5.5. Инъекции horizon-mixins

- Виды: HEAD (в том числе с отменой: `cancellable = true`, помощник возвращает `ControlFlow<R>`, `Break(значение)` досрочно возвращает значение из функции), BEFORE_CALL, AFTER_CALL, AFTER_ASSIGN, MODIFY_EXPRESSION_VALUE, RETURN, MODIFY_ARG, MODIFY_ARGS, MODIFY_CONSTANT, MODIFY_VARIABLE, WRAP_OPERATION, OVERWRITE. Плюс модули поддержки (`[[module]]`), мосты к приватным полям и состояние на экземпляр (`[[state]]`). [ПРОВЕРЕНО: README и docs/mixin-api.md horizon-mixins]
- OVERWRITE конфликтует с любым другим хуком на той же функции. Обобщённые (generic), `const`, `unsafe` функции и функции с чужим ABI как цели не принимаются. [ПРОВЕРЕНО]
- Именованных точек (hook points) для генерации мира нет: в каталоге `native-hooks.json` 427 точек, среди них экраны, тики, команды, загрузка уровней, конфиги, но ни одной про биомы, рельеф или шумы. Поэтому мы используем «сырые» цели (`target = "..."`), которые ломаются при переименовании функции в Horizon. [ПРОВЕРЕНО]
- Хуки экранов (`native_screen_init_post` и т. п.) только наблюдают экран, добавить кнопку на чужой экран через них нельзя. [ПРОВЕРЕНО: docs/native-mods.md]
- Помощник инъекции это файл с ровно одной приватной функцией без атрибутов. Он вставляется **локальной функцией внутри тела цели**, поэтому ему видны типы, импорты и приватные поля модуля цели. Аргументы помощнику передаются привязками (`bindings`), значение привязки может быть только параметром цели или его заимствованием (`self`, `&mut *x`); вызовы и поля в привязках запрещены. [ПРОВЕРЕНО: horizon-mixins docs/mixin-api.md]
- Модуль поддержки `[[module]]` (ключи `id`, `file`, `name`, `source`, необязательно `visibility`) добавляется как `pub(crate) mod <name> { … }` в конец указанного исходного файла. [ПРОВЕРЕНО: docs/boundary-head-and-modules.md]
- Мосты `[[bridge]]` (`GET`, `GET_MUT`, `SET`, `INVOKE`) дают доступ к приватным полям и методам через сгенерированные методы `__horizon_mixins_<мод>_<id>()`. Состояние на экземпляр `[[state]]` добавляет приватное поле в структуру; все литералы структуры объявляются как конструкторы. [ПРОВЕРЕНО: docs/scopes-and-bridges.md, docs/effects-and-state.md]
- Обобщённые `impl` (например, `impl<R> Pipeline<R>`) и `const fn` как цели не принимаются. [ПРОВЕРЕНО]
- Для модов есть конфиги: `native_register_configs`, у мира может быть свой конфиг в `serverconfig/`. [ПРОВЕРЕНО: docs/mods.md]

### 5.6. Сборка нативных модов лаунчером (важно для Windows)

- Лаунчер использует **свой** Rust 1.99.1 (не системный). На Windows x64 цель `x86_64-pc-windows-gnu` с MinGW (GCC 16.2.0). Значит, наш код обязан компилироваться под `x86_64-pc-windows-gnu`. [ПРОВЕРЕНО: docs/native-mods.md, раздел What the launcher does]

- Профили сборки: `performance` (по умолчанию), `dev` (пересборка мода примерно в 6 раз быстрее, игра до 2 раз медленнее), `release`. Для разработки: `horizon-launcher settings native-profile dev`. [ПРОВЕРЕНО]
- **Smart App Control в Windows ломает сборку** (ошибка `os error 4551`): его нужно выключить в «Безопасность Windows → Управление приложениями/браузером → Smart App Control». [ПРОВЕРЕНО]

- Скрипты шаблона нативного мода (`horizon-native-mod-template`, staging через Python) **проверены только на Linux**. На Windows рабочий путь: сборка через лаунчер. Для скриптов шаблона можно использовать WSL2. [ПРОВЕРЕНО: README шаблона]

## 6. Архитектура

### 6.1. Общая схема [ПРЕДЛОЖЕНИЕ]

```
                    ┌──────────────────────────────────────────────────┐
                    │                 litho-core (Rust)                │
  сид, режим,  ───► │  L0 хэш и шумы → L1 плиты → L2 кора и рельеф     │
  версия,           │  → L3 широта, температура, ветер, осадки         │
  (x, z)            │  → L4 реки → L5 классы биомов                    │
                    │  → L6 ванильные параметры C, E, W, T, H          │
                    │  → L7 близость к стыку (лава)                     │
                    │  кэш решётки, без зависимостей, детерминизм      │
                    └──────────┬───────────────┬───────────────┬───────┘
                               │               │               │
                 ┌─────────────▼──┐   ┌────────▼────────┐   ┌──▼──────────────────┐
                 │ litho-sandbox  │   │ мод для Horizon │   │ (план Б) адаптер    │
                 │ карты PNG,     │   │ клей + датапаки │   │ под Fabric, только  │
                 │ метрики, пробы │   │ (раздел 10)     │   │ если Horizon умрёт  │
                 └────────────────┘   └─────────────────┘   └─────────────────────┘
```

Ядро ничего не знает об игре. Оно отвечает на вопрос «какие значения полей в точке `(x, z)` мира с сидом `S` в режиме `M` версии `V`». Песочница и мод это два потребителя одного и того же API, поэтому картинка в песочнице и мир в игре совпадают по построению.

### 6.2. Слои генерации

Слои вычисляются по порядку, каждый может читать только предыдущие.

| Слой | Что считает | Выход | Раздел |
|---|---|---|---|
| L0 | Хэши, случайные числа ячеек, градиентный шум, fBm, искажение домена | примитивы | 7.1, 7.2 |
| L1 | Литосферные плиты: семена, принадлежность точки плите, расстояние до границы, соседи, тип границы | `PlateSample` | 7.3 |
| L2 | Тип коры (материк или океан), базовая высота, профили границ (горы, жёлоба, хребты, рифты), горячие точки, детали | высота `e` в км, «горность» `M`, «плато» `Pl`, «вглубь от берега» `ι` | 7.4 |
| L3a | Полюса-точки, псевдоширота φ, температура с учётом высоты | `φ`, `T` в °C | 7.5 |
| L3b | Ветер по поясам | направление и сила | 7.6 |
| L3c | Осадки: пояс, перенос влаги с ветром, дождевая тень, орографика; испаряемость, биотемпература, индекс сухости | `P` мм/год, `PET/P` | 7.7 |
| L4 | Реки «карандашом» | «сила долины» `r` ∈ [0, 1] | 7.10 |
| L5 | Класс биома (жизненные зоны Холдриджа, упрощённо) | `LifeZone` | 7.8 |
| L6 | Перевод в пять ванильных параметров | `C, E, W, T, H` | 7.9 |
| L7 | Близость к стыку плит для лавы | `λ` ∈ [0, 1] | 7.11 |

Отдельно: «сдвиг точки появления» (7.12), функция одного только сида.

Заметьте, что температура (L3a) не зависит от плит, как и решил автор. Она зависит только от высоты рельефа (холоднее в горах), а высота от плит. Влажность (L3c) зависит от рельефа через дождевую тень и от расположения океанов.

### 6.3. Детерминизм по сиду [ПРЕДЛОЖЕНИЕ]

1. Сид мира (i64 в Minecraft) приводится к `u64` побитово.
2. Из сида и **строковой «соли»** каждого назначения выводится свой подсид: `subseed = splitmix64(seed ^ fnv1a64(соль))`. Соли это константы вида `"plates.seed"`, `"plates.velocity"`, `"poles.seed"`, `"warp.plates.x"` (полный список ведётся в `seed.rs`, менять их нельзя в пределах версии генератора).
3. Случайное число ячейки: `hash(subseed, i, j, k)` (7.1). Никаких генераторов с внутренним состоянием, никакого «следующего случайного числа». Поэтому порядок вычислений не важен.
4. Плавающая точка: только `f64` и базовые операции `+ − × ÷` и `sqrt` (они побитово одинаковы на всех платформах по IEEE 754). Тригонометрию и экспоненту не брать из стандартной библиотеки в местах, от которых зависят решения (тип плиты, класс биома): системные `sin`, `exp` на Windows (MinGW) и Linux (glibc) могут отличаться в последнем бите. Варианты: таблицы констант (12 значений косинуса для месяцев, 7.7), полиномиальные приближения, собственные реализации или крейт `libm` (чистый Rust, есть в `Cargo.lock` Horizon, 5.4). Явный `mul_add` не использовать.
5. Нельзя зависеть от порядка обхода `HashMap`.
6. Порог «на границе» (например, ровно 0,5) не должен давать разный результат из-за округления: сравнения строгие и одинаковые везде.
7. Проверка: golden-тесты (раздел 14) запускаются в CI на Windows (`msvc` и `gnu`) и Linux, значения обязаны совпадать побитово.

### 6.4. Локальность: как считать бесконечный мир по координатам

Главная трудность бесконечного мира: нельзя «сгенерировать всю карту, а потом посмотреть». Любое значение в точке должно вычисляться из **ограниченной окрестности** точки. Таблица ниже фиксирует, насколько далеко смотрит каждый слой (в макро-единицах L, см. 7.0).

| Слой | Что смотрит | Радиус зависимости |
|---|---|---|
| Плиты | Семена в ячейках 5×5 вокруг точки (ячейка 16 L) | ≈ 2 ячейки = 32 L |
| Искажение границ | Шум в самой точке | 0 |
| Кора и рельеф | Свойства 2–3 ближайших плит, горячие точки в ячейках 3×3 (ячейка 24 L) | ≈ 32 L |
| Полюса и широта | Полюса в ячейках 5×5 (ячейка 64 L) | ≈ 128 L |
| Осадки | Луч против ветра длиной 8 L, в каждой точке луча рельеф | 8 L + радиус рельефа |
| Реки (вариант с трассировкой) | Источники в радиусе 3 L, трасса до 3 L | ≈ 6 L + радиус рельефа |
| Сглаживание решётки | ±2 узла решётки | 2 шага решётки |

Все радиусы конечны, значит мир бесконечен «бесплатно»: любая точка, даже на расстоянии 20 млн блоков, считается за одно и то же время.

### 6.5. Как обойтись без глобальной симуляции

Настоящая тектоника и климат это история: плиты двигались миллионы лет, реки прорезали долины, ветер переносил влагу через континенты. Посчитать это для бесконечного мира нельзя. Поэтому план сознательно делает **статичную правдоподобную подделку**, у которой каждое явление заменено локальным правилом:

| Явление в природе | Требует | Наша замена |
|---|---|---|
| Движение плит во времени | История | Каждой плите приписан вектор скорости и угловая скорость. Используются только чтобы классифицировать границу «сходятся / расходятся / скользят». |
| Горообразование | История столкновений | Профиль высоты как функция расстояния до границы и типа границы (7.4). |
| Океаническое дно стареет и опускается | История спрединга | Широкий профиль СОХ: чем дальше от хребта, тем глубже. |
| Перенос влаги ветром | Интегрирование по всей траектории | Луч против ветра ограниченной длины (7.7): влага набирается над океаном и теряется над сушей и на подъёмах. |
| Реки собирают воду со всего бассейна | Обход всего бассейна | Реки «карандашом» (7.10): долины у рифтов, вдоль подножий хребтов и короткие трассы вниз по склону от гор. |
| Климат зависит от сезонов | Время | Сезонный ход учитывается только аналитически, через амплитуду температуры при расчёте биотемпературы (7.7). |

Цена: где-то правдоподобие ниже настоящей модели (например, очень длинные реки через пустыни не появятся). Это принято (реки «упрощённо», раздел 4).

### 6.6. Кэширование и решётка [ПРЕДЛОЖЕНИЕ]

Полная модель в одной точке стоит дорого (поиск плит, несколько октав шума, луч осадков). Игра же спрашивает значения очень часто: на каждый чанк десятки и сотни раз, а LOD тысячи раз на кадр движения. Решение в три уровня:

1. **Эталонный путь** `Generator::sample_macro(x, z)`. Чистая функция, без кэшей. Используется в тестах и как «истина».
2. **Две решётки и поблочные величины.** Каждое поле относится к одной из трёх категорий:

   | Категория | Шаг | Поля | Почему так |
   |---|---|---|---|
   | Грубая решётка | `Δ_c = L/4` (250 блоков в научном режиме, 62,5 в геймплейном) | широта φ, направление на полюс, ветер, влагосодержание μ, континентальность c, осадки P, температура на уровне моря с поправками, сезонная амплитуда | меняются плавно на масштабе L, а считать их дорого (луч осадков) |
   | Точная решётка | `Δ_f = L/16` (62,5 и 15,625 блока) | поле материка `κ_mix`, высота `e`, горность `M`, плато `Pl`, удалённость `ι`, знаковые расстояния для рифтовых и предгорных рек, близость к стыку `λ` | рельеф меняется на долях L, горный пояс шириной около 1 L содержит 16 узлов |
   | Поблочно | каждый вызов | температура с поправкой на высоту, биотемпература, класс зоны с дрожанием границ, расстояние до русел рек, блочные шумы эрозии и странности, итоговые C, E, W, T, H | дёшево, а на решётке потерялось бы (река уже шага решётки) |

   - Шаги решёток заданы в L, поэтому в макро-единицах решётки обоих режимов одинаковы (это нужно для «одной планеты в двух масштабах», раздел 8). Шаги 62,5 и 15,625 точно представимы в двоичной арифметике, узлы `i·Δ` вычисляются без ошибок округления.
   - Узлы привязаны к мировым координатам (кратны шагу), поэтому результат не зависит от того, какой чанк спросили первым.
   - Узлы группируются в **тайлы** 16×16 узлов плюс поля по 2 узла с каждой стороны. Точный тайл покрывает 1 L × 1 L, грубый 4 L × 4 L. Тайл считается целиком один раз и кладётся в кэш.
   - После расчёта узлы тайла **сглаживаются** сепарабельным ядром `[1, 4, 6, 4, 1] / 16` (радиус 2 узла). Это убирает мелкие разрывы (например, у тройных сочленений, 7.3.7) и не трогает крупные формы: горный пояс шириной в сотни блоков больше радиуса сглаживания в 4–10 раз.
   - Значение в блоке получается **бикубической интерполяцией** (Catmull–Rom) по 4×4 узлам.
   - Поля, которые нужны для расчёта других узлов (например, высота `e` в точках луча осадков), берутся из грубой версии высоты, посчитанной в узлах грубой решётки, с билинейной интерполяцией. Так луч из 32 шагов не вызывает дорогой эталонной функции.
3. **Кэш тайлов**: потокобезопасный, ограниченный по памяти (LRU), разбит на шарды (например, 64 шарда по `Mutex`), ключ `(tx, tz)`. Плюс на каждом потоке «последний тайл» в `thread_local`, чтобы соседние запросы не трогали замки.

Важно: кэш хранит только результаты чистых функций. Попал запрос в кэш или нет, ответ одинаковый. Это проверяется тестом (раздел 14).

Песочница при построении «итоговых» карт обязана идти тем же путём (решётка, сглаживание, интерполяция), что и мод, иначе картинки не совпадут с игрой. Эталонный путь в песочнице это отдельный отладочный режим.

### 6.7. Модель интеграции с игрой: почему через пять ванильных параметров [ПРЕДЛОЖЕНИЕ]

Рассматривались два подхода.

**Подход А: подменить входы ванильного генератора (выбран).** Ядро выдаёт пять из шести климатических параметров (C, E, W, T, H). Ванильный генератор Horizon по ним сам строит высоту рельефа (через свои сплайны), выбирает биом (по своей таблице), раскрашивает поверхность, режет пещеры, раскладывает аквиферы, структуры, деревья и строит LOD. Шестой параметр, глубина D, остаётся ванильным: он выводится из рельефа и нужен для подземных биомов.

Плюсы:
- Согласованность «бесплатно»: биом всегда подходит к рельефу (пики на горах, пляжи на берегу, реки в долинах), потому что оба выбираются ванилью из одних и тех же чисел.
- Пещеры, аквиферы, подземные биомы не трогаются, как и решил автор. При этом пещерные биомы сами подстроятся под наш климат: пышные пещеры под влажными регионами, капельниковые под глубинными районами материков.
- LOD Horizon строится из тех же функций, значит дальний рельеф тоже наш.
- Минимум кода в Horizon: одна точка внедрения (5.3) и датапак. Меньше всего ломается при обновлениях Horizon.
- Ванильная структура генерации (деревни на равнинах и т. п.) работает без изменений.

Минусы:
- Высоту мы задаём не напрямую, а через ванильные сплайны рельефа. Очень высокие горы, плато вроде Тибета и глубокие жёлоба ваниль может не воспроизвести. Для научного режима предусмотрено расширение: подменить ещё и функцию «смещения» рельефа (этап I2, 10.1).
- Набор биомов ограничен тем, что умеет ванильная таблица. Например, ванильная «горячая» полоса температуры это всегда пустыня или бесплодные земли. Это учитывается в отображении (7.9).
- Реки в ванили привязаны к нулям параметра W, а он же выбирает варианты биомов. Это ограничивает «карандаш» (7.10).

**Подход Б: подменить выбор биома и высоту напрямую (отклонён для MVP).** Хук на выбор биома и на итоговую плотность. Полный контроль, но: надо самим поддерживать согласованность биома и рельефа, самим решать пещерные биомы, самим собирать плотность с пещерами. Больше точек внедрения, больше поломок при обновлениях Horizon. Остаётся как точечное дополнение на будущее (переопределение биома в отдельных случаях, 10.1, точка №7).

### 6.8. Версионирование генератора [ПРЕДЛОЖЕНИЕ]

- Каждый выпущенный набор формул и чисел имеет номер версии генератора: `v1`, `v2`, …
- Версия входит в имена шумов в датапаке: `litospherity:v1/scientific/continents`. Мир, созданный с `v1`, всегда генерирует новые чанки формулами `v1`, даже после обновления мода. Поэтому на границе старых и новых чанков нет швов.
- Новая версия добавляет новый код, старый остаётся. Удалять старую версию можно только объявив, что миры на ней больше не поддерживаются.
- Golden-тесты (раздел 14) хранят эталоны для каждой выпущенной версии. Если изменение кода меняет эталон выпущенной версии, это ошибка.
- До первого публичного выпуска версия `v0` и может меняться свободно.

## 7. Алгоритмы слоёв

Все числа в этом разделе это **[ПРЕДЛОЖЕНИЕ]**: стартовые значения, которые подбираются в песочнице. Числа, связанные с масштабом, автор оставил **[ПО СИТУАЦИИ]**. Каждое число должно жить в структуре параметров (`Params`, раздел 9), а не быть зашитым в формулу.

Обозначения: `smoothstep(a, b, x)` это стандартная гладкая ступенька (0 при x ≤ a, 1 при x ≥ b, `3t² − 2t³` между, работает и при a > b, тогда ступенька вниз); `lerp(a, b, t) = a + (b − a)·t`; `clamp(x, lo, hi)`; `exp`, `pow` и тригонометрия только через детерминированную реализацию (6.3, п. 4).

### 7.0. Координаты, единицы и режимы

- **Координаты блока** `(x, z)`: целые, `x` растёт на восток, `z` на юг (как в Minecraft). Картинки песочницы рисуются севером вверх: строка изображения растёт вместе с `z`.
- **Макро-единица L.** Все крупные структуры (плиты, материки, полюса, пояса, горные пояса) описываются в макро-единицах. Сколько это блоков, зависит от режима:

| Режим | L, блоков | Смысл | Статус |
|---|---|---|---|
| Научный | 1000 | 1 L ≈ 310 км условной планеты | [ПО СИТУАЦИИ] |
| Геймплейный | 250 | тот же мир, в 4 раза меньше | [ПО СИТУАЦИИ] |

- **Макро-координата** точки: `p = (x / L + p*_x, z / L + p*_z)`, где `p*` это «сдвиг точки появления» (7.12), функция только сида.
- **Высота модели** `e` в километрах условной планеты: −11 (самый глубокий жёлоб) … 0 (уровень моря) … +7 (высочайшие пики). В блоки игры она переводится не напрямую, а через ванильные параметры (7.9).
- **Почему 1 L ≈ 310 км.** Расстояние от полюса до экватора у нас около 32 L (7.5), а на Земле это 10 000 км. Тогда ширина Гималаев (около 300 км) это 1 L, т. е. 1000 блоков в научном режиме и 250 в геймплейном.
- **Блочные величины** (ширина рек, меандры, блочные шумы эрозии и странности, дрожание границ биомов) задаются отдельно для каждого режима и **не масштабируются** вместе с L (раздел 8). Всё, что задано в L (плиты, рельеф, климат, шаги решёток), в обоих режимах одинаково в макро-единицах.

### 7.1. Хэширование и случайные числа ячеек

```text
fnv1a64(строка) -> u64            // соль; offset 0xcbf29ce484222325, prime 0x100000001b3
splitmix64(z) -> u64:
    z = z + 0x9E3779B97F4A7C15                         (с переполнением)
    z = (z ^ (z >> 30)) * 0xBF58476D1CE4E5B9
    z = (z ^ (z >> 27)) * 0x94D049BB133111EB
    return z ^ (z >> 31)
subseed(seed, соль) = splitmix64(seed ^ fnv1a64(соль))
hash3(s, a, b, c) = splitmix64( splitmix64( splitmix64(s ^ (a as u64)*K1) ^ (b as u64)*K2 ) ^ (c as u64)*K3 )
    K1 = 0x9E3779B97F4A7C15, K2 = 0xC2B2AE3D27D4EB4F, K3 = 0x165667B19E3779F9   (умножение с переполнением)
unit(h) = (h >> 11) as f64 * 2^-53            // равномерно в [0, 1)
```

- Несколько случайных чисел для одной ячейки: берём `h0 = hash3(...)`, дальше `h1 = splitmix64(h0)`, `h2 = splitmix64(h1)` и т. д. Порядок использования чисел фиксирован в коде и документирован рядом.
- Отрицательные номера ячеек: `floor(x / G)` в целых `i64`, приведение `i64 → u64` побитовое.
- Тест: таблица известных значений `hash3` для десятка входов (раздел 14). Любой, кто перепишет хэш, обязан получить те же числа.

### 7.2. Шумы

**Градиентный шум 2D** (шум Перлина) [ПРЕДЛОЖЕНИЕ]:
- Узлы целочисленной сетки. В узле `(i, j)` единичный градиент `g = DIRS[hash3(s, i, j, 0) & 255]`, где `DIRS` это таблица из 256 единичных векторов, **записанная в коде константами** (сгенерирована один раз скриптом, хранится в исходнике). Так тригонометрия не участвует во время работы.
- Сглаживание квинтикой `f(t) = t³(t(6t − 15) + 10)`.
- Значение умножается на √2, чтобы диапазон был примерно [−1, 1]. Перед использованием там, где важна граница диапазона, значение обрезается `clamp(−1, 1)`.

**fBm** (сумма октав):
```text
fbm(s, p, λ0, n, gain) = Σ_{k=0}^{n−1} gain^k · noise2(s_k, R_k · p / λk + o_k) / Σ gain^k
λk = λ0 / 2^k;  s_k = splitmix64(s + k);  R_k = поворот на угол 0.61·k рад (константы cos/sin заранее);
o_k = случайный сдвиг из hash3(s, k, 0, 1)
```
Поворот и сдвиг каждой октавы убирают видимое выравнивание по осям.

**Гребневый шум** `ridged(p) = (1 − |noise2(p)|)²`: острые гребни, используется для структуры хребтов.

**Искажение домена** `warp(p) = A · (fbm(sx, p, …), fbm(sz, p, …))`: две независимые fBm по осям.

### 7.3. Литосферные плиты

#### 7.3.1. Семена плит

Каждая плита задана одним семенем (точкой). Принадлежность точки плите: ближайшее семя (ячейки Вороного) после искажения домена.

| Параметр | Значение | Комментарий |
|---|---|---|
| Ячейка семян `G` | 16 L | научный 16 000 блоков, геймплейный 4000 [ПО СИТУАЦИИ] |
| Семян в ячейке | обычно 1; 2 с вероятностью 0,25; 0 с вероятностью 0,35, но **только если оба индекса ячейки чётные** | разброс размеров плит |
| Отступ от края ячейки | 0,08 G | чтобы семена соседних ячеек не слипались |
| Мин. расстояние между двумя семенами одной ячейки | 0,35 G, до 4 попыток, иначе одно семя | |

Почему пустые ячейки только при чётных индексах: тогда у пустой ячейки все 8 соседей непустые, и ближайшее семя гарантированно найдётся в окне 5×5 ячеек (F1 ≤ 1,8 G < 2 G). Без этого правила окно поиска пришлось бы расширять.

Средняя площадь плиты при этих числах около 220 L², то есть типичный поперечник около 17 L (научный 17 000 блоков). Плиты рядом с пустыми ячейками крупнее (до 25–30 L), в ячейках с двумя семенами мельче (8–12 L). Земные крупные плиты 6–10 тыс. км (20–30 L), малые 1–3 тыс. км.

#### 7.3.2. Искажение границ

Без искажения границы Вороного это прямые отрезки, это сразу выдаёт «сетку». Перед поиском плиты точка сдвигается:

```text
q = p + warp_plates(p),   4 октавы, λ0 = 24 L, амплитуда первой октавы A0 = 1.6 L, gain = 0.45
```

Ограничение: искажение не должно «складывать» плоскость (якобиан отображения `p → q` должен оставаться положительным), иначе появятся оторванные кусочки одной плиты внутри другой. В песочнице есть диагностический слой «якобиан искажения» (12.2), по нему подбирается амплитуда. Ориентир: определитель якобиана больше 0,2 везде на тестовых картах.

#### 7.3.3. Поиск плиты и расстояния до границы

```text
plate_query(p):
    q = p + warp_plates(p)
    (ci, cj) = floor(q / G)
    кандидаты = все семена в ячейках ci−2..ci+2, cj−2..cj+2        (до 50 точек)
    s1 = ближайшее к q семя                                         → плита A
    для каждого другого кандидата k:
        β_k = (|q − s_k|² − |q − s1|²) / (2·|s_k − s1|)             // расстояние до серединного перпендикуляра
    B = кандидат с наименьшим β, C = со вторым наименьшим
    d_AB = β_B, d_AC = β_C                                          // ≥ 0, в макро-единицах, в искажённом пространстве
    n_AB = (s_B − s1)/|s_B − s1|, n_AC аналогично                   // нормали к границам, от A наружу
    return PlateSample { A, B, C, d_AB, d_AC, n_AB, n_AC, q }
```

Формула `β` даёт точное расстояние до границы ячейки, если граница A|B действительно проходит рядом, и **оценку снизу** в глубине плиты. Это приемлемо: точность важна только вблизи границ, где стоят горы. Вдали от границ все профили (7.4) затухают до нуля.

#### 7.3.4. Свойства плиты

Из хэша семени `(i, j, k)` (номер ячейки и номер семени в ней) с разными солями:

| Свойство | Распределение | Зачем |
|---|---|---|
| `id` | `hash3(subseed("plates.id"), i, j, k)` | идентификатор, порядок пар |
| `has_continent` | `unit < 0,5` | есть ли на плите материк [ПО СИТУАЦИИ: доля суши] |
| центр материка `c` | семя + равномерный сдвиг в квадрате ±0,25 G | материк не обязательно в центре плиты |
| радиус материка `R` | равномерно 4…9 L | размер материка |
| вытянутость `asp` | равномерно 1…2, направление из таблицы `DIRS` | материки не круглые |
| скорость `v` | направление из `DIRS`, модуль равномерно 0,2…1,0 | тип границы |
| угловая скорость `ω` | равномерно −0,03…+0,03 (на 1 L) | тип границы меняется вдоль длинной границы |
| «возраст» `age` | равномерно 0…1 | какая океаническая плита погружается |

Скорость плиты в точке `q`: `v_A(q) = v_A + ω_A · perp(q − s_A)`, где `perp(x, z) = (−z, x)`. Вращение делает реалистичную вещь: один конец длинной границы может сходиться, а другой расходиться.

Ожидаемая доля суши при `has_continent = 0,5` и `R` 4…9 L: около 28–32 % (Земля 29 %). Если в геймплейном режиме захочется больше суши, поднять долю можно только ценой отказа от «той же планеты в двух масштабах» (раздел 8).

#### 7.3.5. Тип границы

Для пары соседних плит A и B в точке `q`:

```text
Δv = v_A(q) − v_B(q)
c  = Δv · n_AB                      // > 0: A надвигается на B (сближение)
τ  = |Δv.x·n_AB.z − Δv.z·n_AB.x|    // сдвиг вдоль границы
γ_conv = clamp((c − 0.1)/0.5, 0, 1)
γ_div  = clamp((−c − 0.1)/0.5, 0, 1)
γ_tr   = clamp((τ − 0.15)/0.5, 0, 1) · (1 − max(γ_conv, γ_div))
```

Свойство симметрии: с точки зрения плиты B (`n_BA = −n_AB`, `Δv_BA = −Δv_AB`) получаются те же `c` и `τ`. Значит, обе стороны границы согласны в её типе, и рельеф непрерывен через границу.

Тип коры у границы: `χ_A = smoothstep(−0.5, 0.5, κ_A(q))`, `χ_B = smoothstep(−0.5, 0.5, κ_B(q))`, где `κ` это поле материка (7.4.1). `χ = 1` материк, `χ = 0` океан. Плавные значения нужны, чтобы граница «материк/океан» внутри профиля не давала разрывов.

#### 7.3.6. Классификация границ (сводная таблица)

| Сочетание | Вес в точке | Что получается | Земной пример |
|---|---|---|---|
| материк–материк, сближение | `k1 = γ_conv·χ_A·χ_B` | широкий хребет, с одной стороны плато | Гималаи и Тибет |
| материк–океан, сближение | `k2 = γ_conv·\|χ_A − χ_B\|` | жёлоб со стороны океана, вулканическая цепь на материке | Анды |
| океан–океан, сближение | `k3 = γ_conv·(1−χ_A)(1−χ_B)` | жёлоб и островная дуга | Марианы, Алеуты |
| океан–океан, расхождение | `k4 = γ_div·(1−χ_A)(1−χ_B)` | срединно-океанический хребет | Срединно-Атлантический хребет |
| материк–материк, расхождение | `k5 = γ_div·χ_A·χ_B` | рифт: узкая долина или молодое море с плечами | Восточная Африка, Красное море |
| материк–океан, расхождение | `k6 = γ_div·\|χ_A − χ_B\|` | хребет смещён в океан, на материке лёгкое опускание | редкий случай, упрощённо |
| скольжение | `k7 = γ_tr` | слабые уступы и вытянутые понижения | Сан-Андреас |

#### 7.3.7. Тройные сочленения

У точки две ближайшие «чужие» плиты B и C. Вклад каждой взвешивается:

```text
w_B = exp(−d_AB / 0.4),  w_C = exp(−d_AC / 0.4),  ŵ_B = w_B/(w_B + w_C),  ŵ_C = w_C/(w_B + w_C)
```

Когда точка подходит к месту, где ближайшая чужая плита меняется с B на C, веса равны 0,5/0,5, и рельеф не прыгает. Строгой непрерывности у самих тройных точек это не гарантирует (с разных сторон границы A|B «третья» плита оценивается по-разному). Остаточные разрывы малы и сглаживаются фильтром решётки (6.6). В песочнице есть слой «разрывы» (12.2), который подсвечивает скачки высоты больше порога между соседними узлами.

### 7.4. Кора и макрорельеф

#### 7.4.1. Поле материка κ

Для плиты X с материком:

```text
(u, w) = поворот(q − c_X) в оси эллипса
ρ = sqrt( (u / (R·sqrt(asp)))² + (w / (R/sqrt(asp)))² )
κ_X(q) = R·(1 − ρ) + 1.5 L · fbm(q; λ0 = 6 L, 4 октавы, gain 0.5)
```

`κ > 0` внутри материка, `κ ≈ 0` береговая линия, единицы примерно «макро-единицы до берега». Для плиты без материка `κ_X = −6 L`.

**Смешивание через границу.** На самой границе две плиты дают разные `κ`, поэтому они смешиваются:

```text
b(d) = 1 − smoothstep(0, 1.0 L, d)
κ_mix = κ_A + 0.5·ŵ_B·b(d_AB)·(κ_B − κ_A) + 0.5·ŵ_C·b(d_AC)·(κ_C − κ_A)
```

На границе A|B с обеих сторон получается `(κ_A + κ_B)/2`, разрыва нет.

#### 7.4.2. Базовая высота от коры (км)

| Диапазон κ_mix | Формула | Смысл |
|---|---|---|
| `κ ≥ 0` | `0.6·(1 − exp(−κ/1.5))` | от 0 км у берега до 0,6 км вглубь материка |
| `−0.5 ≤ κ < 0` | `−0.2·(−κ/0.5)` | шельф до −0,2 км |
| `−1.5 ≤ κ < −0.5` | `−0.2 − 4.3·smoothstep(0, 1, −κ − 0.5)` | континентальный склон |
| `κ < −1.5` | `−4.5` | абиссальная равнина |

#### 7.4.3. Профили границ

Асимметричные профили задаются через **знаковое расстояние** `σ`: для каждой пары выбирается «верхняя» сторона (у субдукции надвигающаяся плита, у столкновения сторона плато), `σ = +d` на верхней стороне и `σ = −d` на нижней. Обе стороны вычисляют одно и то же `σ = 0` на границе, поэтому профиль непрерывен.

Кто «сверху»:
- материк–океан: материк;
- океан–океан: более молодая плита (меньший `age`), старая тонет;
- материк–материк: сторона плато выбирается битом хэша пары `hash(min(id), max(id))`.

| № | Профиль, км | Параметры по умолчанию |
|---|---|---|
| U1 столкновение | `H_col·exp(−(d/W_col)²) + 0.4·H_col·plat(σ)`, `plat(σ) = smoothstep(−W_col, 0.5·W_col, σ)·(1 − smoothstep(1.2·W_col, 3.5·W_col, σ))` | `H_col = 4.5`, `W_col = 0.6 L` |
| U2 субдукция под материк | `−H_tr·exp(−((σ + d_tr)/w_tr)²) + H_arc·exp(−((σ − d_arc)/w_arc)²)` | `H_tr = 3.5`, `d_tr = 0.15 L`, `w_tr = 0.12 L`, `H_arc = 4.0`, `d_arc = 0.9 L`, `w_arc = 0.45 L` |
| U3 островная дуга | `−H_tr·exp(−((σ + d_tr)/w_tr)²) + H_isl·exp(−((σ − d_isl)/w_isl)²)·(0.55 + 0.45·n_isl(q))` | `H_isl = 4.2`, `d_isl = 0.6 L`, `w_isl = 0.18 L`, `n_isl` шум с λ = 1,2 L |
| U4 СОХ | `H_r·exp(−(d/W_r)²) − H_ax·exp(−(d/w_ax)²)` | `H_r = 2.2`, `W_r = 1.8 L`, `H_ax = 0.4`, `w_ax = 0.06 L` |
| U5 рифт | `−H_rift·(1 + γ_div)·exp(−(d/W_rift)²) + H_sh·exp(−((d − 1.6·W_rift)/W_rift)²)` | `H_rift = 0.9`, `W_rift = 0.25 L`, `H_sh = 0.7` |
| U6 расхождение материк–океан | `0.5·H_r·exp(−((σ + 0.8)/W_r)²) − 0.2·exp(−(σ/0.5)²)` | |
| U7 трансформ | `0.35·exp(−(d/0.12)²)·n_tr(q)` | `n_tr` шум с λ = 2 L |

Сумма вкладов от границ:

```text
U_b = Σ_{N ∈ {B, C}} ŵ_N · Σ_{i=1..7} k_i(A, N) · U_i(d_AN, σ_AN)
```

Проверка правдоподобия (числа на выходе): глубина жёлоба `−4.5 − 3.5 = −8` км, гребень СОХ `−4.5 + 2.2 = −2.3` км, хребет столкновения `0.6 + 4.5 ≈ 5` км плюс детали, плато около 2,4 км над базой, вулканическая цепь Анд 4–5 км, дно рифта при сильном расхождении ниже уровня моря (узкое море), при слабом выше (цепь озёр и долин).

#### 7.4.4. Горячие точки

```text
сетка ячеек G_h = 24 L; в ячейке горячая точка с вероятностью 0.3, позиция h с отступом 0.1·G_h
U_h(p) = Σ по точкам в окне 3×3:  H_h·(1 − 0.7·χ(h))·exp(−(|p − h|/R_h)²)
         + цепочка: k = 1..5,  центр h − k·0.9 L·v̂(h),  высота H_h·(1 − 0.17k)·(1 − 0.7·χ(h)),  радиус R_h·(1 + 0.1k)
H_h = 4.8 км, R_h = 0.5 L, v̂(h) = направление скорости плиты, на которой стоит h
```

В океане получаются вулканические острова с цепочкой затонувших гор (как Гавайи и Императорский хребет), на материке плато высотой около 1,4 км (как Йеллоустоун). Это «научная» деталь, её можно выключить параметром.

#### 7.4.5. Детализация макрорельефа

```text
χ_q = smoothstep(−0.5, 0.5, κ_mix)
e_det = χ_q·0.25·fbm(q; 3 L, 4 окт.) + (1 − χ_q)·0.3·fbm(q; 4 L, 3 окт.) + M·0.6·ridged_fbm(q; 0.4 L, 3 окт.)
```

Это ещё «макро»: детали в сотни блоков. Мелкий рельеф (холмы, скалы, пещеры) рисует ваниль своими 3D-шумами.

#### 7.4.6. Итог слоя L2

```text
e  = e_base(κ_mix) + U_b + U_h + e_det                                   // км
M  = clamp( (положительные части U1, U2, U3, U5-плечи, U_h) / 3.0 км + 0.25·k7·exp(−(d/0.3)²), 0, 1 )   // «горность»
Pl = 0.4·H_col·plat(σ)·k1 / (0.4·H_col)                                  // «плато», 0..1
ι  = если e > 0: max(κ_mix, min(1.0, 0.5·e)), иначе 0                    // «вглубь от берега», L
```

`ι` это приближённое расстояние до берега. Для материков оно берётся из поля `κ` (которое по построению похоже на расстояние до края материка). Для островов дуг и горячих точек, где `κ < 0`, но высота выше моря, берётся небольшое значение от высоты. Точное расстояние до берега нелокально, приближение достаточно для отображения в ванильную континентальность (7.9).

### 7.5. Полюса-точки, псевдоширота и температура (слой L3a)

Решение автора [РЕШЕНО]: температура не зависит от плит, она задаётся положением «относительно солнца». Мир плоский и бесконечный, поэтому вместо двух полюсов шара у нас бесконечно много **полюсов-точек**, вокруг каждой холодно, от них расходятся пояса, которые сливаются в широкие экваториальные зоны. Ниже предложенная реализация этой идеи [ПРЕДЛОЖЕНИЕ].

#### 7.5.1. Полюса и псевдоширота φ

```text
сетка полюсов G_P = 64 L, ровно один полюс в каждой ячейке, отступ от края 0.1·G_P
q_P = p + warp_poles(p)          // 3 октавы, λ0 = 40 L, A0 = 4 L, gain 0.5: пояса не идеально круглые
(P1, F1), (P2, F2) = ближайший и второй по близости полюс к q_P (окно 5×5 ячеек)
t  = F1 / (F1 + F2)              // 0 на полюсе, 0.5 на «экваторе»
φ0 = 90·(1 − 2t)                 // градусы псевдошироты
φ  = clamp(φ0 + 3·fbm(p; λ0 = 10 L, 3 окт., gain 0.5), 0, 90)
```

- **Почему ровно один полюс в ячейке.** Пустые ячейки дали бы гигантские полярные «территории» с поясами шириной в десятки L, а двойные слишком узкие. Один полюс на ячейку даёт ровный шаг поясов: расстояние от полюса до экватора около `G_P/2 = 32 L` (отсюда и оценка «1 L ≈ 310 км» в 7.0).
- **Почему окна 5×5 достаточно.** Пусть точка лежит в ячейке `[0, 1)²` (в единицах `G_P`). Свой полюс не дальше `0.8·√2 ≈ 1.13`. Из двух соседей слева и справа хотя бы один не дальше `√(1.4² + 0.8²) ≈ 1.61`. Значит, `F2 ≤ 1.61 < 2`, а все полюса вне окна 5×5 дальше 2. Окно даёт точные F1 и F2.
- **Геометрия.** Вблизи полюса изолинии φ это окружности. Ближе к экватору они превращаются в скруглённые многоугольники, а там, где сходятся три «территории» полюсов, образуется широкая экваториальная область (F1 ≈ F2 на большой площади). Это и есть «зоны растут и сливаются в большие экваториальные зоны» из замысла автора.
- **Все полюса одинаковые («северные»).** Различать северные и южные полюса нельзя: граф соседства ячеек Вороного содержит треугольники, его не раскрасить в два цвета. Последствие описано в 7.6.

**Направление на полюс** `n̂` нужно для ветра (7.6). Считается аналитически, без конечных разностей:

```text
û1 = (q_P − P1)/F1,  û2 = (q_P − P2)/F2
g  = F2·û1 − F1·û2                // ∇t с точностью до положительного множителя
n̂  = −g / |g|                     // направление роста φ, то есть «на север»
ê  = (−n̂.z, n̂.x)                  // «восток»: поворот n̂ на 90° по часовой стрелке на карте с севером вверх
```

Проверка: если `n̂ = (0, −1)` (на картинке вверх, «север»), то `ê = (1, 0)`, то есть восток вправо. Искажение `warp_poles` в направлении не учитывается, это даёт ошибку в несколько градусов, которая не видна.

#### 7.5.2. Температура на уровне моря

Среднегодовая температура на уровне моря как функция псевдошироты:

```text
T_sl(φ) = 28 − 52·(φ/90)^1.6        [°C]
```

| φ | T_sl | Земля, среднее по широте (ориентир) |
|---|---|---|
| 0° | 28,0 | 26–27 |
| 30° | 19,0 | около 20 |
| 45° | 10,8 | 10–12 |
| 60° | 0,8 | около 0 |
| 75° | −10,8 | около −12 |
| 90° | −24,0 | от −18 (Арктика) до −49 (Антарктида) |

#### 7.5.3. Высота, континентальность, сезоны

```text
c   = континентальность ∈ [0, 1]: 0 у наветренного берега, 1 в глубине материка (считается в 7.7)
ΔT_c = c·( 2·(1 − smoothstep(25, 45, φ)) − 6·smoothstep(40, 70, φ) )     // глубь материков: теплее в тропиках, холоднее в высоких широтах
T   = T_sl(φ) + ΔT_c − 6.5·max(e, 0)       // суша; e в км (7.4), 6,5 °C на км высоты
SST = max(T_sl(φ), −1.8)                    // температура поверхности моря, для океанских биомов
A_lat(φ) = 1 + 24·smoothstep(5, 75, φ)     // полуамплитуда сезонного хода, °C
A   = A_lat(φ)·(0.25 + 0.75·c)              // у моря сезоны мягкие, в глубине материка резкие
T_m = T + A·cos_m,  m = 0..11               // средняя температура месяца
cos_m = ±0.9659258, ±0.7071068, ±0.2588190  // каждое значение дважды, это cos(2π(m + 0,5)/12) записанные константами
T_bio = (1/12)·Σ clamp(T_m, 0, 30)          // биотемпература по Холдриджу
T_min = T − 0.9659258·A                      // самый холодный месяц, нужен для «снежных» биомов (7.8)
```

Зачем сезоны в статичном мире. Сезонов как механики нет [РЕШЕНО], но без сезонной амплитуды классификация ломается: место со среднегодовой −5 °C при амплитуде 20 °C имеет тёплое лето и растит тайгу (Якутия), а при амплитуде 2 °C это ледяная пустыня. Амплитуда учитывается аналитически, без времени.

### 7.6. Ветер (слой L3b)

Ветер нужен только внутри модели влажности [РЕШЕНО: «ветер не фича»]. Используются три классических пояса постоянных ветров, привязанных к псевдошироте [ПРЕДЛОЖЕНИЕ]:

```text
d_trade = normalize(−0.5·n̂ − 0.87·ê)    // пассаты (0–30°): к экватору и на запад
d_west  = normalize( 0.35·n̂ + 0.94·ê)   // западные ветры (30–60°): к полюсу и на восток
d_polar = normalize(−0.5·n̂ − 0.87·ê)    // полярные восточные (60–90°): от полюса и на запад
w_t = 1 − smoothstep(25, 35, φ)
w_w = smoothstep(25, 35, φ)·(1 − smoothstep(55, 65, φ))
w_p = smoothstep(55, 65, φ)
V   = s(φ)·(w_t·d_trade + w_w·d_west + w_p·d_polar)     // вектор ветра, |V| ≤ 1, без нормировки
```

Сила ветра `s(φ)`, кусочно-линейная по точкам:

| φ | 0 | 5 | 15 | 30 | 45 | 60 | 75 | 90 |
|---|---|---|---|---|---|---|---|---|
| s | 0,25 | 0,30 | 1,00 | 0,30 | 1,00 | 0,40 | 0,60 | 0,30 |

Минимумы у экватора (штиль, ITCZ), на 30° («конские широты») и на 60° (полярный фронт). Сумма без нормировки сама уменьшает ветер в переходных зонах, где векторы поясов гасят друг друга.

**Известный артефакт.** Все полюса «северные» (7.5.1), поэтому на экваторе между двумя территориями пассаты с двух сторон имеют противоположную восточно-западную составляющую (на Земле оба пассата дуют на запад). Получается полоса сдвига ветра вдоль экватора. Она маскируется слабым ветром у экватора (`s ≈ 0,25`). В песочнице слой ветра (12.2) обязан показывать, что заметных последствий для влажности нет. Если они будут, вариант исправления: на экваторе уменьшить вклад переноса влаги до нуля (оставить только конвекционные осадки).

Влияние гор на направление ветра не моделируется. Муссонов нет (это сезонное явление, а мир статичен).

### 7.7. Осадки, континентальность, испаряемость (слой L3c)

Задача [РЕШЕНО]: влажность «по-умному»: климатический пояс, дождевая тень при постоянном ветре в поясе, и то, откуда дует ветер (с океана или с материка). Сам по себе океан рядом влажность не гарантирует.

Предложенная модель [ПРЕДЛОЖЕНИЕ] это перенос влаги вдоль линии тока ветра, ограниченной длины. Она даёт сразу все нужные эффекты: пустыни на западных берегах в поясе пассатов (ветер с суши), влажные наветренные берега, сухие внутренние районы материков, дождевую тень за хребтами.

#### 7.7.1. Линия тока против ветра

```text
N = 32 шага, Δs = 0.25 L (длина 8 L)
x_0 = p
для k = 1..N:
    v = V(x_{k−1});  если |v| < 0.05: v = направление предыдущего шага (на первом шаге d_trade)
    x_k = x_{k−1} − Δs·v/|v|              // шаг ПРОТИВ ветра, направление пересчитывается в каждой точке
```

#### 7.7.2. Перенос влаги по ветру

Влагосодержание воздуха `w` (безразмерное, 1 ≈ насыщенный тёплый морской воздух) считается от дальнего конца линии к точке:

```text
w_sat(x) = clamp(0.3 + 0.035·T_sl(φ(x)), 0.3, 1.25)     // тёплый воздух несёт больше влаги
w = (e(x_N) < 0) ? w_sat(x_N) : 0.5·w_sat(x_N)           // на дальнем конце: над морем насыщен, над сушей наполовину
для k = N−1 .. 0:
    если e(x_k) < 0:                                      // над морем (и внутренними морями)
        w = w + (w_sat(x_k) − w)·(1 − exp(−Δs/ℓ_oc))
    иначе:                                                // над сушей
        w = w·exp(−Δs/ℓ_land)                             // постепенная потеря влаги
        w = w·exp(−max(0, e(x_k) − e(x_{k+1})) / h_oro)   // подъём в гору: влага выпадает на наветренном склоне
μ = w (значение в самой точке p)
ℓ_oc = 1.0 L,  ℓ_land = 6 L,  h_oro = 1.5 км
```

Подъём на 4 км оставляет `exp(−4/1,5) ≈ 7 %` влаги. Поэтому за высоким хребтом по ветру сухо (дождевая тень), даже если до океана недалеко.

#### 7.7.3. Континентальность

```text
m_ind = Σ_k ω_k·[e(x_k) < 0] / Σ_k ω_k,   ω_k = exp(−k·Δs / 3 L)       // доля моря против ветра, ближние точки важнее
c_ray = 1 − m_ind
c_iso = smoothstep(0, 5 L, ι)                                            // в штиль: просто удалённость от берега
c     = lerp(c_iso, c_ray, smoothstep(0.1, 0.4, |V(p)|))
```

#### 7.7.4. Осадки

```text
P_c(φ) = 1900·exp(−(φ/11)²) + 900·exp(−((φ − 50)/13)²)      // крупные зоны подъёма воздуха: экваториальная (ITCZ) и полярный фронт
a(φ)   = 0.15 + 0.55·exp(−(φ/15)²)                            // доля осадков от местного круговорота, у экватора большая
V̂      = V(p)/|V(p)|
slope  = max(0, (e(p) − e(p − 0.25 L·V̂)) / 0.25)             // наветренный подъём, км на L
U      = 0.6 + 0.5·min(slope, 3)                               // подъём воздуха: у берега 0.6, на крутом склоне до 2.1
P      = P_c(φ)·(a + (1 − a)·μ) + 1500·max(|V(p)|, 0.6)·μ·U  // мм в год
```

Первое слагаемое это «пояс»: дожди в зонах, где воздух поднимается сам (у экватора и на 50–60°), ослабленные, если воздух сухой. Второе это перенос: влажный ветер с моря, особенно на подъёме в горы. Обе части зависят от `μ`, то есть от того, откуда пришёл воздух.

#### 7.7.5. Испаряемость и индекс сухости

```text
PET = 58.93·T_bio        // мм в год, формула Холдриджа
R   = PET / max(P, 10)   // индекс сухости: > 1 сухо, < 1 влажно
```

### 7.8. Классификация: жизненные зоны (слой L5)

Классификация упрощённо следует схеме жизненных зон Холдриджа [ПРЕДЛОЖЕНИЕ]: пояс по биотемпературе, «провинция влажности» по индексу сухости. Выход это ванильный биом, к которому мы стремимся, точнее его ячейка `(t, h)` в ванильной таблице (раздел 7.9, приложение A).

#### 7.8.1. Пояса и провинции

| Пояс | T_bio, °C | | Провинция | R = PET/P |

| П5 субтропический | 18–24 | | К6 пергумидная | < 0,5 |
| П6 тропический | > 24 | | | |

Перед классификацией к входам добавляется «дрожание» границ шумом в блоках (не в L), чтобы границы биомов не были гладкими изолиниями: `T_bio' = T_bio + j_T·fbm(x/240, z/240)`, `log2 R' = log2 R + j_R·fbm(…)`. Амплитуды `j_T`, `j_R` разные по режимам (раздел 8).

**Океаны** классифицируются отдельно по температуре моря: `SST < 0` → frozen (t = 0), 0–10 → cold (1), 10–18 → обычный (2), 18–24 → lukewarm (3), > 24 → warm (4). Глубокий или нет, решает C (7.9.1).

### 7.9. Перевод в ванильные параметры (слой L6)

Это сердце подхода А (6.7): из наших полей получаются пять чисел C, E, W, T, H, по которым ваниль строит рельеф и выбирает биом. Приложение A содержит справочные полосы ванили.

**Главное правило непрерывности.** C, E и W управляют рельефом через ванильные сплайны. Если они скачут, в мире появляются стены и обрывы. Поэтому C, E, W обязаны быть **непрерывными** функциями координат: только гладкие функции от непрерывных полей, никаких «если класс = X, то значение = Y». T и H в ванили влияют только на выбор биома (и на поиск точки появления), поэтому они могут быть ступенчатыми (класс → центр полосы). Это различие проверяется тестом непрерывности (раздел 14).

**Диапазон.** Все пять значений лежат в [−1, 1]. C ограничено снизу −1,0: при C < −1,05 ваниль ставит грибные острова (приложение A), они нам не нужны [ПО СИТУАЦИИ: можно разрешить для вулканических островов в геймплейном режиме].

#### 7.9.1. Континентальность C

На море C считается из глубины `e` (км), на суше из удалённости от берега `ι` (в L, поэтому в обоих режимах распределение одинаковое). Кусочно-линейные таблицы:

| Море: e, км | 0 | −0,2 | −1,5 | −2,5 | −3,5 | −4,5 | ≤ −8 |
|---|---|---|---|---|---|---|---|
| C | −0,17 | −0,30 | −0,40 | −0,45 | −0,52 | −0,70 | −0,98 |

| Суша: ι, L | 0 | 0,05 | 0,5 | 2 | 5 | 10 | ≥ 20 |
|---|---|---|---|---|---|---|---|
| C(ι) | −0,17 | −0,11 | 0,03 | 0,30 | 0,60 | 0,85 | 1,00 |

```text
C_land = lerp(−0.17, C(ι), smoothstep(0, 0.15 км, e))     // на самом берегу C = −0.17 с обеих сторон
```

Последняя строка нужна для внутренних морей и рифтовых озёр: там `κ` большое (глубоко внутри материка), но берег есть, и без неё C прыгнуло бы с −0,17 до C(κ). Проверки: гребень СОХ (−2,3 км) даёт C ≈ −0,44, то есть ванильный «ocean», а абиссаль (−4,5 км) «deep_ocean». На картах ванильных биомов срединные хребты будут видны полосами обычного океана среди глубокого. Жёлоб (−8 км) это тоже deep_ocean: ваниль не умеет делать дно глубже (это расширение I2, раздел 10).

#### 7.9.2. Эрозия E

```text
E_base = 0.25 + 0.15·fbm_b(x/λ_E, z/λ_E)                  // в основном полоса E4: равнины и леса
E_mnt  = −0.85 + 0.25·fbm_b(…)                             // полосы E0–E1: горы
M_e    = smoothstep(0.05, 0.6, M)
E      = lerp(E_base, E_mnt, M_e)
E      = lerp(E, −0.30, Pl·(1 − M_e))                      // плато: полоса E2, ваниль ставит плато-биомы
```

`fbm_b` означает шум в блочных координатах (масштаб `λ_E` задаётся по режиму, раздел 8).

**Болота** [ПО СИТУАЦИИ, в v0 можно выключить]: на влажных низинах (`e < 0.15 км`, `M < 0.05`, `R < 0.6`, рядом река `r > 0.2` или берег `ι < 0.3 L`) эрозия плавно поднимается к 0,75 (полоса E6), и ваниль ставит swamp или mangrove_swamp. Переход проходит через узкую полосу E5 (0,45–0,55), где ваниль делает «разбитый» рельеф (windswept). Переход делается коротким, результат проверяется в песочнице.

#### 7.9.3. Странность W

W одновременно управляет формой рельефа (через `PV = 1 − |3|W| − 2|`, зависит только от |W|) и выбором вариантов биомов (знак W). Поэтому W собирается из модуля и знака:

```text
m_plain = 0.18 + 0.10·fbm_b(x/λ_W, z/λ_W)                 // равнины: срезы low/mid, мягкие холмы
m_mnt   = 0.30 + 0.40·ridged_b(x/λ_W, z/λ_W)               // горы: от седловин (0.3) до пиков (около 2/3)
m       = lerp(m_plain, m_mnt, smoothstep(0.1, 0.5, M))
m       = lerp(m, 0.33, Pl·(1 − smoothstep(0.1, 0.5, M)))  // плато: срез mid
m       = min(m, 0.75)
s       = clamp(3·fbm_b(x/λ_s, z/λ_s), −1, 1)              // мягкий знак, непрерывный
W       = s·m·(1 − r)                                      // r: сила реки (7.10)
```

- Пики ванили (срез |W| ≈ 0,57–0,77 при низкой эрозии) попадают на гребни `ridged_b` внутри горных поясов.
- Знак меняется только через ноль, поэтому W непрерывна. Цена: вдоль линий `s = 0` модуль |W| проходит через 0, и ваниль рисует там долину, а на равнине реку. Это «шумовые реки», похожие на ванильные. Их частоту задаёт `λ_s` (раздел 8, вопрос в 17).
- Знак выбирает варианты: ледяные шипы вместо снежной равнины, подсолнечниковые равнины, бамбуковые джунгли и т. п. При шуме в знаке они займут около половины площади своих классов, как в ванили.
- Ориентация хребтов вдоль границы плиты (анизотропный шум в системе координат границы) это возможное улучшение [ПРЕДЛОЖЕНИЕ, не в v1].

#### 7.9.4. Температура T и влажность H

Значения выдаются как центр ванильной полосы для ячейки `(t, h)` из 7.8:

| Полоса | t0 | t1 | t2 | t3 | t4 | | h0 | h1 | h2 | h3 | h4 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| Центр | −0,70 | −0,30 | 0,00 | 0,37 | 0,77 | | −0,65 | −0,22 | 0,00 | 0,20 | 0,45…0,85 |

Для h4 значение растёт с влажностью: `H = 0.45 + 0.40·smoothstep(0.5, 0.25, R)`. Ванильные пышные пещеры требуют H ≥ 0,7, так что они окажутся под самыми влажными лесами.

Для моря: `T` по полосам SST (7.8), `H = 0`. Какую классификацию применить (сушу или море), решает итоговое C: при `C ≥ −0.19` (берег и суша) сухопутная, иначе морская. Так граница одна и не дрожит.

### 7.10. Реки «карандашом» (слой L4)

Решение автора [РЕШЕНО]: реки упрощённо, «карандашом». Если выйдет плохо, продумаем отдельно.

В ванили река это долина вдоль линии W ≈ 0 (срез «valley», |W| < 0,05) при подходящих C и E. Ваниль сама прорезает русло до уровня моря и ставит речной биом (замёрзшую реку в холоде). В горах (низкая эрозия, далеко от берега) в такой долине воды нет, получается сухая долина. Наши реки это просто способ обнулить W вдоль нужных линий: `W = s·m·(1 − r)`, где `r ∈ [0, 1]` сила реки [ПРЕДЛОЖЕНИЕ].

#### 7.10.1. Виды рек v1

| Вид | Где | Формула `r` (максимум из всех видов) |
|---|---|---|
| Рифтовые | вдоль оси континентального рифта (k5, 7.3.6) | `k5·(1 − smoothstep(0, w_b, \|σ·L + A_m·noise2(p_b/λ_m)\|))` |
| Предгорные | вдоль подножия хребтов столкновения на низкой стороне, `σ_f = −1.6·W_col` | `k1·(1 − smoothstep(0, w_b, \|(σ − σ_f)·L + A_m·noise2(…)\|))` |
| Трассированные | от истоков в горах вниз по склону до моря или большой реки | `1 − smoothstep(0, w_b(ℓ), d_seg)` |
| Шумовые | линии смены знака W | сами получаются из `s` (7.9.3) |

Здесь `σ·L` переводит знаковое расстояние из L в блоки, `A_m` и `λ_m` амплитуда и масштаб меандров в блоках (`A_m = 60`, `λ_m = 400` блоков), `w_b` полуширина реки в блоках (раздел 8), `d_seg` расстояние в блоках до ближайшего отрезка трассы. На море `r = 0` (реки кончаются у берега, устье рисует ваниль).

#### 7.10.2. Трассировка рек от гор

```text
сетка истоков G_r = 2 L; в каждой ячейке кандидат в случайной точке (отступ 0.1·G_r)
исток принят, если M ≥ 0.35, e ≥ 0.8 км, P ≥ 500 мм и unit(hash) < 0.6
трасса: шаг δ = 0.05 L, не больше 60 шагов (3 L)
    dir_k = normalize( 0.5·dir_{k−1} + 0.5·(−∇e(x_k)/|∇e(x_k)|) ), затем поворот на угол 0.6·noise2(x_k / 0.5 L) рад
    x_{k+1} = x_k + δ·dir_k
    стоп: e < 0 (дошли до моря), r_рифт или r_предгорн > 0.5 (влились в большую реку),
          |∇e| < 0.02 км/L пять шагов подряд (плоская котловина), или 60 шагов
трасса короче 1 L отбрасывается
полуширина растёт вниз по течению: w_b(ℓ) = w_b0·(1 + 0.6·min(1, ℓ/3 L))
```

- `∇e` берётся центральными разностями (шаг 0,05 L) по сглаженной **решётке** `e` (6.6), а не по эталонной функции: так трасса дешевле и одинакова у всех тайлов.
- Локальность: трасса не длиннее 3 L, поэтому тайлу нужны истоки только из ячеек в радиусе `3 L + 1 L`, то есть в окне 7×7 ячеек истоков. Каждая трасса считается один раз и кэшируется по номеру ячейки истока.
- Отрезки трасс, задевающие тайл, хранятся в тайле с простой сеткой корзин 8×8. Расстояние `d_seg` считается для каждого блока точно, а не интерполяцией решётки: шаг решётки (62,5 блока в научном режиме) больше ширины реки.

#### 7.10.3. Что не делаем

- Не собираем воду со всего бассейна: это глобальная задача (6.5). Очень длинных рек через полматерика не будет.
- Реки не текут «по высоте»: ваниль держит воду рек на уровне моря и прорезает долину. Река через высокое плато превратится в каньон или сухую долину. Это ограничение подхода А.
- Озёр как отдельной сущности нет. Внутренние моря и рифтовые озёра появляются сами, где рельеф ниже уровня моря.

### 7.11. Лава у стыков плит (слой L7)

Решение автора [РЕШЕНО]: пещеры не трогаем, минимум: лавовые озёра на глубине около −50, которых в ванили «много где попало», привязать к стыкам плит.

Где в ванили (и в Horizon) берётся глубинная лава [ПРОВЕРЕНО, 5.3]:
1. **Глобальный выбор жидкости**: всё, что ниже Y = −54 и затоплено, затоплено лавой.
2. **Лава аквиферов**: ячейка аквифера с уровнем жидкости ≤ −10 становится лавовой, если `|lava(x div 64, y div 40, z div 64)| > 0.3`.

Наше поле близости к стыку [ПРЕДЛОЖЕНИЕ]:

```text
λ_N = ŵ_N·(0.4 + 0.6·max(γ_conv, γ_div))·exp(−(d_AN·L / w_lava)²)        // для N ∈ {B, C}, d_AN·L в блоках
λ_h = max по горячим точкам: exp(−(|p − h|·L / w_lava)²)
λ   = max(λ_B, λ_C, λ_h, λ_bg)                                         // λ_bg: фоновая доля
```

| Параметр | Научный | Геймплейный | Статус |
|---|---|---|---|
| `w_lava`, блоков | 300 | 120 | [ПО СИТУАЦИИ] |
| `λ_bg` | 0,05 | 0,15 | [ПО СИТУАЦИИ] |

Как это попадает в игру:
- **Лава аквиферов** (этап I3, без кода в Horizon, если поле `lava` в настройках аквиферов 26.3 подменяется датапаком): значение поля `lava_field = λ·(0.6 + 0.4·noise3(ячейка))`. Ванильное правило `|значение| > 0,3` тогда срабатывает почти везде у стыков и почти нигде вдали. Поле вызывается в координатах ячеек 64×40×64, поэтому в датапаке у узла шума ставится `xz_scale = 64`, `y_scale = 40`: наш шум получает координаты, близкие к блочным.
- **Глобальный выбор жидкости** (этап I3, нужна точка внедрения №4 в разделе 10): ниже −54 лава только при `λ ≥ 0.5`, иначе вести себя как выше −54 (вода до уровня моря, обычная логика аквиферов). Трудность: функция не знает, какой мир генерируется (10.1).

Последствие для игрока: в научном режиме стыки плит далеко друг от друга (около 17 000 блоков), и глубинной лавы вдали от них почти не будет. Отсюда фоновая доля `λ_bg`.

### 7.12. Сдвиг точки появления

Ванильный поиск точки появления перебирает точки в радиусе 2048 блоков от (0, 0) [ПРОВЕРЕНО, 5.3]. В научном режиме 2048 блоков это 2 L. Если (0, 0) попадёт в середину океана шириной 10 L, суши в радиусе поиска не будет, и игрок появится в воде.

Решение [ПРЕДЛОЖЕНИЕ]: сдвинуть макро-координаты так, чтобы блок (0, 0) попал в хорошее место планеты. Сдвиг `p*` входит в формулу макро-координаты (7.0).

```text
кандидаты: k = 0..255, точка c_k = (unit(h_k)·2 − 1, unit(h'_k)·2 − 1)·100 L, h_k из subseed("spawn")
для каждого кандидата эталонной функцией (без кэша и без сдвига):
    годится, если 0.1 ≤ e ≤ 1.5 км, κ_mix ≥ 1 L, M < 0.2, 25° ≤ φ ≤ 55°, 0.5 ≤ R ≤ 2
p* = первый годный кандидат; если ни один не подошёл, кандидат с наибольшим κ_mix среди e > 0
```

- `p*` это функция только сида и версии генератора (макро-поля одинаковы в обоих режимах), поэтому оба режима одной планеты начинаются в одном и том же месте планеты.
- Считается один раз при создании генератора, около 256 эталонных расчётов, порядка десятков миллисекунд.
- Ванильный поиск затем сам выберет точку в радиусе 2048 блоков, и там гарантированно суша умеренного климата.

### 7.13. Свои биомы из ванильных блоков

Желание автора [РЕШЕНО как «потом, если легко»]: например, очень глубокие океаны.

Факт [ПРОВЕРЕНО, 5.3]: Horizon отбрасывает новые биомы из датапаков, потому что у игры нет для них числовых id, цветов и звуков. Добавить биом значит править реестры клиента и сервера нативным кодом в нескольких местах. Это не «легко», поэтому в план v1 не входит.

Что можно сделать без новых биомов:
- «Очень глубокий океан» как форма рельефа: в научном режиме подменить ванильную функцию смещения рельефа (расширение I2, раздел 10), тогда жёлоба станут глубже, а биом останется `deep_ocean`.
- Вернуться к вопросу после выпуска v1, если в Horizon появится API регистрации биомов.

## 8. Два режима

### 8.1. Что сказал автор

[РЕШЕНО] Два режима. **Геймплейный**: как ванильная генерация плюс большие биомы, «уменьшенная версия научного». **Научный**: максимально правдоподобно, менее играбельно, например по 1000 блоков одного биома. Режим выбирается в меню при создании мира. Масштаб [ПО СИТУАЦИИ].

### 8.2. Одна планета в двух масштабах [ПРЕДЛОЖЕНИЕ]

Один и тот же сид в обоих режимах даёт **одну и ту же планету**: те же плиты, материки, полюса, пояса, осадки. Геймплейный мир это научный, уменьшенный в 4 раза по горизонтали (`L = 250` вместо `L = 1000` блоков). Отличаются только блочные детали, которые подбираются для каждого режима отдельно.

Почему так:
1. Одна модель, одни макро-параметры, одна настройка в песочнице. Не надо поддерживать две разные планеты.
2. Это буквально прочтение слов автора «уменьшенная версия научного».
3. Есть сильный автоматический тест: макро-поля геймплейного режима в точке `(x, z)` равны макро-полям научного в точке `(4x, 4z)` (раздел 14).
4. Игрок может «разведать» научную планету в геймплейном мире.

Цена: в геймплейном режиме нельзя поменять, например, долю суши или расстояние между полюсами, не сломав п. 3. Если по картинкам захочется именно этого, вводится отдельный набор макро-параметров геймплейного режима, это новое решение (запись в журнал решений, раздел 19).

### 8.4. Выбор режима при создании мира

Факты [ПРОВЕРЕНО, 5.3]: тип мира на экране создания это закрытый список в коде Horizon, пресеты мира из датапаков не читаются. Поэтому «свой тип мира» без правки кода экрана невозможен. Зато на экране создания есть More → Data Packs.

План [ПРЕДЛОЖЕНИЕ]:

| Шаг | Как выбирается режим | Требует кода в Horizon | Этап |
|---|---|---|---|
| 1 | Два датапака-архива `litospherity_v1_scientific.zip` и `litospherity_v1_gameplay.zip`. Игрок перетаскивает нужный в окно Data Packs при создании мира. Ваниль копирует пак в папку мира. | нет | I1 |
| 2 | Те же паки как встроенные «feature»-паки в списке Data Packs (папка `<resources>/data/minecraft/datapacks/`), включаются галочкой. | возможно (как положить файлы в ресурсы, 10.5) | I1b |
| 3 | Своя кнопка или переключатель «Litospherity: научный / геймплейный / выкл.» на экране создания мира. | да, миксины на экран (хуки экранов только наблюдают, 5.5) | I4, после v1 |

Правило: включается ровно один пак Litospherity. Если включены оба, действует верхний по приоритету (его файлы перекрывают файлы второго), и режим будет его. Мод пишет предупреждение в лог, если видит шумы двух режимов в одном мире.

Тип мира (вкладка World) должен быть «Обычный» (Normal). Варианты «Большие биомы» и «Расширенный» используют в ванили отчасти другие функции плотности. Переопределять ли их тоже, решается в T71 после проверки имён файлов 26.3.

### 8.5. Где хранятся режим и версия

- Имя шума в датапаке содержит версию генератора и режим: `litospherity:v1/scientific/continents`. Точка внедрения №1 (10.2) разбирает имя и создаёт генератор нужной версии и режима. Отдельного конфига мира не нужно.
- Мир помнит включённые датапаки (в `level.dat`), значит режим и версия закреплены за миром навсегда.
- **Ловушка версий.** Если пак встроенный (шаг 2 в 8.4) и мод обновится, содержимое пака у старых миров тоже обновится. Поэтому выпущенный пак никогда не меняется: новая версия генератора это новый пак с новым id (`litospherity_v2_scientific`), а старый остаётся в моде. Пак из архива в папке мира (шаг 1) заморожен сам по себе, с ним проблемы нет.

### 9.4. Публичный API (эскиз) [ПРЕДЛОЖЕНИЕ]

```rust
pub enum Mode { Scientific, Gameplay }
pub enum GenVersion { V0, V1 }
#[derive(Clone, Copy)] pub enum Field { Continents, Erosion, Ridges, Temperature, Vegetation, Lava, Offset }

pub struct Generator { /* сид, режим, версия, Params, p*, кэши */ }

impl Generator {
    /// Создание дорогое (поиск p*), вызывать один раз на мир.
    pub fn new(seed: i64, mode: Mode, version: GenVersion) -> Result<Self, GenError>;

    /// Эталон: все поля в точке, без кэшей. Для тестов, песочницы, поиска p*.
    pub fn sample_reference(&self, x: f64, z: f64) -> FullSample;

    /// Быстрый путь через решётку и кэш. Ровно те же формулы, что видит игра.
    pub fn sample(&self, x: f64, z: f64) -> FullSample;

    /// То, что зовёт мод: одно ванильное поле в блочных координатах.
    pub fn field(&self, field: Field, x: f64, y: f64, z: f64) -> f64;

    /// Колонка значений для одного (x, z): для быстрой реализации add_to_volume.
    pub fn field_column(&self, field: Field, x: f64, z: f64) -> f64;

    pub fn spawn_shift(&self) -> (f64, f64);
    pub fn params(&self) -> &Params;
}

pub struct FullSample {
    pub plate: PlateSample,                 // 7.3: A, B, C, d_AB, d_AC, типы границ
    pub e_km: f64, pub m: f64, pub pl: f64, pub iota_l: f64,          // 7.4
    pub phi_deg: f64, pub t_c: f64, pub sst_c: f64, pub amp_c: f64,   // 7.5
    pub t_bio: f64, pub t_min: f64,
    pub wind: [f64; 2],                                                // 7.6
    pub moisture: f64, pub cont: f64, pub p_mm: f64, pub pet_mm: f64, pub ratio: f64,  // 7.7
    pub river: f64,                                                    // 7.10
    pub zone: LifeZone, pub cell: VanillaCell,                         // 7.8
    pub vanilla: VanillaParams,                                        // 7.9: c, e, w, t, h
    pub lava: f64,                                                     // 7.11
}
```

Правила API: внутри всё в `f64`, перевод в `f32` только на границе с Horizon. Функции генерации не паникуют и не возвращают NaN (в отладочной сборке `debug_assert!`, в выпускной NaN заменяется нулём и пишется в лог один раз). В горячем пути нет выделения памяти.

### 9.5. Параметры

- Все числа раздела 7 живут в `Params` (вложенные структуры по слоям). В коде формул чисел нет.
- `Params::defaults(version, mode)` возвращает замороженный набор. Для выпущенной версии он не меняется никогда (6.8).
- `params_hash()` (FNV-1a от канонической текстовой записи) пишется в лог мода и в подпись картинок песочницы. По нему видно, какими параметрами сделана картинка.
- Песочница умеет загружать переопределения из TOML (`--params my.toml`), чтобы подбирать числа без перекомпиляции. Найденные числа переносятся в код новой версии (или `v0` до первого выпуска).
- `xtask params-doc` генерирует `docs/PARAMS.md` из `Params`, чтобы таблица в документации не расходилась с кодом.

## 10. Интеграция с Horizon

Всё в этом разделе относится к коммиту `f319701`. Сырые цели (`target`) ломаются при переименовании функций в Horizon, поэтому раздел 10.6 описывает процедуру переезда.

### 10.1. Точки внедрения

| № | Что | Механизм | Цель (target) | Этап | Статус |
|---|---|---|---|---|---|
| 1 | Подмена шумов `litospherity:*` нашими полями | HEAD, `cancellable = true` | `horizon_core::density::graph::seeded::SeededContext::noise` | I1 (MVP) | цель [ПРОВЕРЕНО]; компиляция помощника [НЕ ПРОВЕРЕНО] |
| 2 | Подключение полей к рельефу и климату | датапак: переопределить функции плотности `minecraft:overworld/{continents, erosion, ridges, temperature, vegetation}` | нет кода | I1 (MVP) | имена из фикстуры Horizon [ПРОВЕРЕНО]; ванильные файлы 26.3 [НЕ ПРОВЕРЕНО] |
| 3 | Лава аквиферов у стыков | датапак: поле `lava` в объекте `aquifers` настроек шума; либо точка №1 для ванильного шума лавы только в наших мирах | нет кода или №1 | I3 | ключ `aquifers.lava` [ПРОВЕРЕНО]; ссылка или встроенное значение в ванили 26.3 [НЕ ПРОВЕРЕНО] |
| 4 | Лава ниже −54 только у стыков | HEAD на `<GlobalFluidPicker as FluidPicker>::compute` | `horizon_world::worldgen::aquifer` | I3 | [НЕ ПРОВЕРЕНО]: функция не знает, чей мир (см. ниже) |
| 5 | Паки режимов в списке Data Packs | файлы в `<resources>/data/minecraft/datapacks/` | возможно без кода | I1b | путь [ПРОВЕРЕНО]; как туда положить файлы [НЕ ПРОВЕРЕНО] |
| 6 | Своя высота рельефа (научный режим) | датапак: `minecraft:overworld/offset` (или аналог 26.3) → наш шум `…/offset` через №1 | нет кода | I2 | [НЕ ПРОВЕРЕНО] |
| 7 | Точечная замена биома | хук на выбор биома | уточнить | после v1 | не исследовано |
| 8 | Переключатель режима на экране создания мира | миксины на `horizon_client::title::create_world` | уточнить | I4, после v1 | не исследовано |

**Почему этого достаточно.** В 26.3 поля маршрутизатора `temperature`, `vegetation`, `continents`, `erosion`, `ridges`, `depth` это ссылки на именованные функции плотности `minecraft:overworld/<поле>` [ПРОВЕРЕНО: `tools/fixtures/datapacks/horizon_worldgen_test/data/minecraft/worldgen/noise_settings/overworld.json` в репозитории Horizon]. Значит, достаточно переопределить пять маленьких файлов функций плотности. Большой файл `noise_settings/overworld.json` (а это данные Mojang) копировать и менять не нужно, если только не понадобится п. 3 со встроенным значением. Все производные функции (сплайны высоты, «складки» `PV`, глубина) ссылаются на эти пять по имени и подхватят наши значения сами.

**Трудность точки №4.** `GlobalFluidPicker` хранит только уровень моря и id блоков (`aquifer.rs`, строки 31–37). Его конструктор `new` это `const fn`, а единственное место создания находится в `Pipeline<R>::new` с обобщённым `impl` [ПРОВЕРЕНО]. Ни то ни другое horizon-mixins не принимает как цель (5.5). Варианты, которые проверяет T77:
1. Глобальный «активный мир Litospherity», который выставляет помощник точки №1 при создании наших шумов. Риск: несколько миров в одном процессе (например, выход в меню и загрузка ванильного мира) требуют аккуратного сброса.
2. `[[state]]` на `GlobalFluidPicker` (5.5): поле «генератор Litospherity или ничего». Под вопросом, примет ли планировщик литерал внутри `const fn`.
3. Хук на необобщённую функцию аквифера, у которой есть доступ и к выбору жидкости, и к нашему полю лавы.
4. Отказаться от №4 и обойтись п. 3: лава аквиферов будет у стыков, но сплошной слой лавы ниже −54 останется ванильным.

### 10.2. Точка №1: манифест и помощник (эскиз)

```toml
# mod/horizon-mixin.toml.in (эскиз, НЕ ПРОВЕРЕН сборкой; ключи по docs horizon-mixins)
[mod]
id = "litospherity"
version = "@VERSION@"

[compatibility]
horizon_revision = "f319701e8c9ab657ff562250b3ba07b2d654e3bc"

[[crate]]
id = "core"                       # общее пространство id с инъекциями и модулями
path = "crates/litho-core"         # папка внутри бандла с Cargo.toml
dependent = "horizon-core"         # какой пакет Horizon будет зависеть от крейта (по умолчанию horizon-client)

[[module]]
id = "glue"
file = "crates/horizon-core/src/lib.rs"    # в конец этого файла добавится `pub(crate) mod litospherity_glue { … }`
name = "litospherity_glue"
source = "glue/litospherity_glue.rs"

[[injection]]
id = "noise"
kind = "HEAD"
cancellable = true
target = "horizon_core::density::graph::seeded::SeededContext::noise"
helper = "glue/noise_hook.rs"
bindings = [
  { name = "ctx",   ty = "&SeededContext", value = "self" },
  { name = "graph", ty = "&DensityGraph",  value = "graph" },
  { name = "id",    ty = "NoiseId",        value = "id" },
]
```

```rust
// mod/glue/noise_hook.rs (эскиз; файл помощника содержит ровно одну приватную функцию без атрибутов)
fn litospherity_noise(
    ctx: &SeededContext,
    graph: &DensityGraph,
    id: NoiseId,
) -> std::ops::ControlFlow<Result<std::sync::Arc<dyn crate::noise::Noise>, crate::density::graph::CompileError>> {
    let Ok(entry) = graph.noise_entry(id) else {
        return std::ops::ControlFlow::Continue(());
    };
    match crate::litospherity_glue::noise_for_name(ctx.seed, &entry.name) {
        Some(noise) => std::ops::ControlFlow::Break(Ok(noise)),
        None => std::ops::ControlFlow::Continue(()), // не наш шум или неизвестная версия: обычный путь Horizon
    }
}
```

Почему так [ПРОВЕРЕНО по docs horizon-mixins и исходникам Horizon]:
- Значение привязки (`value`) может быть только параметром цели или его заимствованием (`self`, `graph`, `id`); вызовы и поля в привязках запрещены. Поэтому `self.seed` и `graph.noise_entry(id)` вычисляются **внутри** помощника.
- Помощник становится локальной функцией внутри тела цели, в модуле `seeded.rs`. Там видны приватное поле `SeededContext::seed`, приватный метод `DensityGraph::noise_entry` (он в родительском модуле `graph`) и структура `NoiseEntry` (`pub(super)`, объявлена в `seeded.rs`). Типы `SeededContext`, `DensityGraph`, `NoiseId` в области видимости через `use super::*;` в начале `seeded.rs`.
- `NoiseId` это `Copy`, поэтому передача `id` в помощник не мешает исходному телу функции.
- `CompileError` публичный (`horizon_core::density::graph::CompileError`).

Что остаётся проверить сборкой (T72): что планировщик принимает такие привязки и пути типов, что `crate::litospherity_glue` виден из `seeded.rs` (модуль `pub(crate)` в корне крейта, значит виден), что `litho_core` подключается к `horizon-core` через `dependent`.

Замечания:
- Досрочный возврат обходит внутренний кэш экземпляров `SeededContext` (`instances`). Это нормально: наш шум лёгкий, он держит `Arc` на общий генератор мира.
- Особый случай `minecraft:nether/*` в начале функции нас не касается: наш HEAD выполняется раньше и для таких имён возвращает `Continue`.
- Неизвестная версия генератора в имени шума: пишем ошибку в лог и возвращаем `Continue`. Мир сгенерируется с фиктивным шумом (рельеф будет странным), но игра не упадёт.

### 10.3. Клей: `LithoNoise` и реестр генераторов

```rust
// mod/glue/litospherity_glue.rs (эскиз; содержимое модуля без обёртки `mod`; НЕЛЬЗЯ писать //! и #![...])
pub struct NoiseSpec { pub version: litho_core::GenVersion, pub mode: litho_core::Mode, pub field: litho_core::Field }

/// "litospherity:v1/scientific/continents" -> NoiseSpec
pub fn parse_noise_name(name: &str) -> Option<NoiseSpec> { /* строгий разбор, неизвестное -> None */ }

/// Точка входа для помощника точки №1.
pub fn noise_for_name(seed: i64, name: &str) -> Option<std::sync::Arc<dyn crate::noise::Noise>> {
    parse_noise_name(name).and_then(|spec| noise_for(seed, spec))
}

/// Один Generator на (seed, mode, version), общий для всех полей мира и для LOD.
static REGISTRY: std::sync::Mutex<Vec<((i64, u8, u8), std::sync::Weak<litho_core::Generator>)>> = std::sync::Mutex::new(Vec::new());

pub fn noise_for(seed: i64, spec: NoiseSpec) -> Option<std::sync::Arc<dyn crate::noise::Noise>> { /* найти живой Weak или создать */ }

#[derive(Debug)]
pub struct LithoNoise { gen: std::sync::Arc<litho_core::Generator>, field: litho_core::Field }

impl crate::noise::Noise for LithoNoise {
    fn range(&self) -> Result<[f32; 2], crate::noise::NanRange> { Ok([-1.0, 1.0]) }
    fn get2(&self, x: f64, z: f64) -> f32 { self.gen.field(self.field, x, 0.0, z) as f32 }
    fn get3(&self, x: f64, y: f64, z: f64) -> f32 { self.gen.field(self.field, x, y, z) as f32 }
    // add_to_volume: переопределить. Реализация по умолчанию зовёт get3 для КАЖДОЙ точки объёма
    // (порядок z, x, y). Наши поля (кроме лавы) от y не зависят: считать одно значение на колонку
    // (x, z) и прибавлять его ко всем y этой колонки, умножив на amplitude.
}
```

Факты, на которые опирается эскиз [ПРОВЕРЕНО]:
- Трейт `Noise`: `range() -> Result<[f32; 2], NanRange>`, `get2(x, z) -> f32`, `get3(x, y, z) -> f32`, `add_to_volume(buffer, volume, xz_scale, y_scale, amplitude) -> Result<(), DensityError>` с реализацией по умолчанию по точкам. Значения `f32`.
- Узел `minecraft:noise` без сдвигов компилируется в `NoiseSampler`, который вызывает `noise.get3(x·xz_scale, y·y_scale, z·xz_scale)` от целых координат, а для объёмов `add_to_volume(…, xz_scale, y_scale, 1.0)`. При `xz_scale = 1` наш шум получает блочные координаты.
- Диапазон узла берётся из определения шума в датапаке, а не из `range()` экземпляра (5.3). Поэтому `range()` у нас скорее для порядка, а важен диапазон фиктивного определения (10.4).

Точные пути типов (`crate::noise::NanRange`, `DensityVolume`, `DensityError`) сверяются при первой сборке (T72).

Потокобезопасность: `Noise: Send + Sync`. Генератор разделяется между потоками генерации чанков и LOD. Кэш тайлов шардирован, «последний тайл» в `thread_local` хранится с id генератора (чтобы два мира не путались).

### 10.4. Датапаки

Формат 26.3 отличается от 1.21 [ПРОВЕРЕНО по декодеру Horizon `crates/horizon-world/src/worldgen/density.rs` и фикстурам]:
- узел шума: `{"type": "minecraft:noise", "noise": "<id>", "xz_scale": …, "y_scale": …}`, сдвиги `shift_x/y/z` необязательны (в 1.21 был отдельный `shifted_noise`); шум только ссылкой, встроенное определение не поддерживается;
- кэш: один тип `{"type": "minecraft:cache", "input": …}` (в 1.21 были `flat_cache`, `cache_2d` и т. п.);
- бинарные узлы: `left` / `right`, унарные: `input`;
- определение шума: `{"base_amplitude": 1.0, "base_octave": -7, "octave_count": 2}`;
- `pack.mcmeta` в фикстуре Horizon: `{"pack": {"description": "…", "min_format": 121, "max_format": 121}}`.

Состав пака `litospherity_v1_scientific` [ПРЕДЛОЖЕНИЕ]:

```text
pack.mcmeta
data/minecraft/worldgen/density_function/overworld/continents.json
data/minecraft/worldgen/density_function/overworld/erosion.json
data/minecraft/worldgen/density_function/overworld/ridges.json
data/minecraft/worldgen/density_function/overworld/temperature.json
data/minecraft/worldgen/density_function/overworld/vegetation.json
data/litospherity/worldgen/noise/v1/scientific/continents.json      # фиктивные определения шумов
data/litospherity/worldgen/noise/v1/scientific/erosion.json
data/litospherity/worldgen/noise/v1/scientific/ridges.json
data/litospherity/worldgen/noise/v1/scientific/temperature.json
data/litospherity/worldgen/noise/v1/scientific/vegetation.json
# этап I3: лава аквиферов (файл зависит от результата T71)
# этап I2: своя высота рельефа (overworld/offset или аналог 26.3)
```

Пример переопределения:

```json
{
  "type": "minecraft:cache",
  "input": {
    "type": "minecraft:noise",
    "noise": "litospherity:v1/scientific/continents",
    "xz_scale": 1.0,
    "y_scale": 0.0
  }
}
```

Пример фиктивного определения (значения никогда не используются, наш HEAD подменяет экземпляр, но **диапазон** граф берёт отсюда):

```json
{ "base_amplitude": 4.0, "base_octave": 0, "octave_count": 1 }
```

`base_amplitude = 4` выбран с запасом, чтобы объявленный диапазон точно накрывал [−1, 1]. Точное значение диапазона для такого определения проверяет T72 (вызвать `range()` у определения в тестовой сборке).

Нужна ли обёртка `minecraft:cache` и какая была у ванильных функций 26.3, проверяет T71. Если ванильные файлы `overworld/*` устроены иначе (например, внутри них ещё что-то, на что ссылаются другие функции), обёртку повторяем точно, меняя только узел шума.

Паки генерируются `xtask` из шаблонов для каждой пары (версия, режим), руками JSON не правится.

### 10.5. Бандл и сборка

- `xtask bundle` собирает папку бандла: `horizon-mixin.toml` (из шаблона), копию `crates/litho-core`, файлы `mod/glue/*.rs`, паки (как архивы для ручной установки). Результат проверяется командой лаунчера `native-build` (раздел 11) и упаковывается в `.hnmod` для выпуска.
- Может ли бандл положить файлы паков в ресурсы игры (точка №5), проверяет T76. Если нет, I1 идёт через ручную установку архива (8.4, шаг 1), это полностью рабочий путь.
- Бандл не содержит файлов Mojang. Наши JSON написаны нами и содержат только ссылки на наши шумы.

### 10.6. Закрепление версии Horizon и переезд на новый коммит

[РЕШЕНО] Версия Horizon фиксируется. Мод закреплён на `horizon_revision = f319701…`. Ночная сборка хранится навсегда под тегом `nightly-source/2026-11-05-f319701`, так что закреплённый мод собирается всегда.

Переезд на новый коммит (делается редко, по необходимости, например если игроки массово перешли на новую сборку):
1. Посмотреть изменения Horizon между коммитами в файлах: `horizon-core/src/density/graph/{seeded.rs, mod.rs, compiler.rs}`, `horizon-core/src/noise/stack.rs`, `horizon-core/src/density/mod.rs`, `horizon-world/src/worldgen/{router.rs, aquifer.rs, aquifer/*, density.rs, generator.rs}`, `docs/world-generation.md`, `docs/native-mods.md`.
2. Обновить `horizon_revision`, собрать бандл. Ошибки `E_TARGET_NOT_FOUND` и подобные значат, что цель переименована: найти новую.
3. Прогнать внутриигровой контроль (раздел 14.5): тот же сид, те же координаты, те же значения полей (команда отладки или лог) и те же биомы в контрольных точках.
4. Записать в `docs/HORIZON.md`: новый коммит, что поменялось, что проверено.
5. Генератор при переезде не меняется (версия генератора и версия Horizon независимы).

### 10.7. Риски версий Horizon

| Что может измениться в Horizon | Последствие | Что делаем |
|---|---|---|
| Переименование `SeededContext::noise` или его сигнатуры | мод не собирается на новом коммите | закрепление; процедура 10.6 |
| Диапазон узла начнут брать из экземпляра | ничего плохого | — |
| Новые оптимизации, полагающиеся на свойства шума (например, на кэш экземпляров) | неверный рельеф | контроль 14.5 при переезде |
| Изменение формата датапаков | пак не грузится | шаблоны в xtask, контроль при переезде |
| Официальный API генерации | можно упростить мод | перейти на него (это возможный будущий PR, сейчас не делаем: 2.2 Н8) |
| Проект Horizon заброшен | новых сборок нет, закреплённая работает | план Б (10.8) |

### 10.8. План Б: Fabric

[РЕШЕНО в обсуждении как запасной путь] Та же Rust-библиотека под Fabric. Эскиз [ПРЕДЛОЖЕНИЕ]:
- `litho-core` собирается как `cdylib` с C-ABI функциями `litho_new(seed, mode, version) -> handle`, `litho_field(handle, field, x, y, z) -> f32`, `litho_free(handle)`.
- Тонкий мод Fabric регистрирует свой тип функции плотности (например, `litospherity:field`), который вызывает библиотеку через Java FFM API (Panama) или JNI. Это неизбежная прослойка на Java/Kotlin на 100–300 строк, вся наука остаётся в Rust. Перед началом этой работы нужно согласие автора (он принципиально против Java; прослойка не ядро, но решать ему).
- Датапаки почти те же, только вместо `minecraft:noise` с нашим именем стоит наш тип функции плотности.
- Нативные библиотеки собираются для Windows, Linux, macOS.

## 11. Сборка и запуск на Windows

Автор работает на Windows, Horizon ставит сам и проверяет в игре сам [РЕШЕНО]. Ниже два независимых пути: песочница (обычный Rust) и мод (через лаунчер Horizon).

### 11.1. Песочница

1. Установить Rust через `rustup` (https://rustup.rs). Для цели по умолчанию `x86_64-pc-windows-msvc` нужен Visual Studio Build Tools с компонентом «Разработка классических приложений на C++». Если ставить его не хочется, можно `rustup default stable-x86_64-pc-windows-gnu`.
2. `git clone https://github.com/Eblanitus/LithoMuchi && cd LithoMuchi`
3. Карты: `cargo run -p litho-sandbox --release -- render --seed 42 --mode gameplay --layers all --size 2048 --out out\seed42`
4. Открыть PNG в `out\seed42`. Описание слоёв и того, как их оценивать, в разделе 12.
5. Значения в точке: `cargo run -p litho-sandbox --release -- probe --seed 42 --mode scientific --at 1200,-3400`

### 11.2. Мод в Horizon

1. Выключить Smart App Control: «Безопасность Windows» → «Управление приложениями и браузером» → Smart App Control → выкл. Иначе сборка падает с `os error 4551` [ПРОВЕРЕНО: docs/native-mods.md].
2. Поставить сборку Horizon того коммита, на котором закреплён мод (ночная 2026-11-05), или использовать «Build anyway» на другой ночной сборке на свой риск.
3. Включить профиль разработки: `horizon-launcher settings native-profile dev` (пересборка мода примерно в 6 раз быстрее, игра до 2 раз медленнее).
4. Собрать: `cargo run -p xtask -- bundle --out target\bundle`, затем `horizon-launcher native-build target\bundle --instance <имя> --trust-native-code`. Первая сборка скачивает Rust лаунчера и идёт 20–30 минут [ПРОВЕРЕНО: docs]. Путь к `horizon-launcher` на Windows уточняется в T70.
5. Лог сборки: `native/build.log` в папке данных лаунчера, в окне лаунчера кнопка Build log.
6. В игре: Singleplayer → Create World → вкладка World: тип «Обычный» → More → Data Packs → перетащить `litospherity_v1_scientific.zip` (или геймплейный) в окно и включить → Create.
7. Проверка: по чеклисту 14.5.

### 11.3. Linux или WSL2 для разработчиков

Скрипты шаблона нативного мода (`horizon-native-mod-template`, staging на Python) проверены только на Linux [ПРОВЕРЕНО]. На Linux или в WSL2 с их помощью можно применить бандл к исходникам Horizon и гонять `cargo check`/`cargo test` прямо в staged-workspace, не запуская лаунчер. Это самый быстрый цикл для работы над клеем (раздел 10.3). Окончательная проверка всё равно через лаунчер под Windows, потому что там своя цель `x86_64-pc-windows-gnu`.

### 11.4. Частые проблемы

| Симптом | Причина | Что делать |
|---|---|---|
| `os error 4551` при сборке | Smart App Control | выключить (11.2, п. 1) |
| `E_TARGET_NOT_FOUND` | сборка Horizon не того коммита, цель переименована | ставить закреплённую сборку или процедура 10.6 |
| Мод исключён из сборки с объяснением | не применилась инъекция | читать `native/build.log`, сверить цель и привязки |
| Ошибка линковки или компиляции только под Windows | разница `gnu`/`msvc`, редкие API | CI собирает `x86_64-pc-windows-gnu` (раздел 14) |
| Мир ванильный, хотя пак включён | пак не включился или имена шумов не совпали с ожидаемыми модом | лог мода: строка «Litospherity: создан генератор v1/scientific, seed …» должна быть |
| Рельеф «рваный», стены | C/E/W разрывны или объявленный диапазон шума уже наших значений | слой «разрывы» в песочнице, проверка 10.4 |
| Долго генерируются дальние области | нагрузка LOD | профиль 14.4, параметры кэша |

## 12. Песочница

### 12.1. Зачем и для кого

[РЕШЕНО] Первая веха проекта: все генеративные функции в песочнице и карта сверху, чтобы посмотреть, как выглядит мир, до всякой интеграции с игрой. Главный потребитель картинок это автор: он решает, красиво ли и правдоподобно ли. Второй потребитель разработчики: песочница это главный отладчик генератора.

Песочница вызывает **тот же** `litho-core`, что и мод, и по умолчанию тем же быстрым путём (решётка, сглаживание, интерполяция, 6.6). Поэтому картинка совпадает с тем, что будет в игре, с точностью до того, что дорисует ваниль (3D-шум рельефа, деревья, пещеры).

### 12.2. Команды [ПРЕДЛОЖЕНИЕ]

| Команда | Что делает |
|---|---|
| `render` | рисует выбранные слои в PNG: `--seed`, `--mode`, `--version`, `--center x,z` (блоки), `--size` (пиксели), `--bpp` (блоков на пиксель), `--layers`, `--path fast\|reference`, `--params file.toml`, `--out` |
| `atlas` | одна большая картинка: основные слои одного сида рядом, с легендами и подписью (сид, режим, версия, `params_hash`) |
| `sweep` | сетка миниатюр одного слоя для N сидов (по умолчанию 16): разнообразие и редкие провалы |
| `probe` | все поля `FullSample` в точке, включая промежуточные (номера плит, `d`, `γ`, `k1…k7`, `μ`, `c`…), текстом или JSON |
| `stats` | метрики по области (12.4), отчёт в Markdown и JSON |
| `seams` | проверка швов тайлов и непрерывности C/E/W, тепловая карта скачков |
| `checkpoints` | для сида выбирает 10 контрольных точек разных биомов и печатает координаты, ожидаемый биом и примерную высоту: по ним автор сверяет игру (14.5) |
| `golden` | запись и проверка эталонов (14.3) |
| `bench` | замеры скорости эталонного и быстрого путей |
| `vanilla-preview` (опция, T65) | какой биом выберет ваниль по нашим C, E, W, T, H, по таблице из отчёта `biome_parameters/overworld.json`, который Horizon берёт из вашей копии игры. Таблицу в репозиторий не кладём (это данные Mojang), путь к ней передаётся параметром. |

Масштабы по умолчанию: обзор планеты 2048×2048 пикселей, 64 блока на пиксель в научном режиме и 16 в геймплейном. Это одна и та же область планеты (около 130 L), потому что режимы это одна планета в разных масштабах (8.2). Региональный вид: 4 блока на пиксель.

### 12.3. Слои карт

| Слой | Что показывает | На что смотреть |
|---|---|---|
| `plates` | плиты случайными цветами, границы цветом типа (красный сближение, синий расхождение, зелёный скольжение), семена, стрелки скоростей | нет «сетки»; плиты разного размера; тип границы меняется вдоль длинных границ |
| `jacobian` | определитель якобиана искажения границ | нигде нет значений ниже 0,2 (7.3.2) |
| `crust` | поле материка `κ_mix`, береговая линия | материки неправильной формы, есть пассивные окраины |
| `height` | высота `e` в км, гипсометрическая раскраска и отмывка рельефа | горы на стыках, жёлоба у дуг, СОХ в океанах, рифты |
| `mpi` | горность `M`, плато `Pl`, удалённость `ι` | плато у столкновений с одной стороны |
| `poles` | φ с изолиниями через 10°, полюса, экватор | пояса растут от полюсов и сливаются в экваториальные зоны |
| `temp` | `T`, `T_bio`, `T_min` | холоднее в горах; континентальные зимы |
| `wind` | стрелки ветра по сетке поверх рельефа, сила оттенком | три пояса; на экваторе слабый ветер (артефакт сдвига, 7.6) |
| `moisture` | `μ` и континентальность `c` | влага убывает вглубь материка и за хребтами |
| `precip` | `P` (логарифмическая шкала), `PET`, `R` с границами провинций | пустыни на западных берегах в 15–30°, влажные наветренные берега, дождевая тень |
| `zones` | жизненные зоны (пояс × провинция), классическая палитра Холдриджа | порядок зон от полюса к экватору |
| `biomes` | целевой ванильный биом по таблице 7.8.2 и океаны по SST | правдоподобные соседства (нет пустыни рядом с тундрой) |
| `vanilla` | C, E, W, T, H по отдельности | C, E, W без скачков |
| `rivers` | `r`, отрезки трасс | реки от гор к морю, рифтовые и предгорные реки |
| `lava` | `λ` | лава вдоль стыков |
| `spawn` | точка `p*` и круг радиуса 2048 блоков | суша умеренного климата |
| `seams` | скачки между соседними блоками | пусто |

Палитры свои (не копировать палитры чужих программ-карт). Каждая картинка подписана: сид, режим, версия, `params_hash`, масштаб, слой.

### 12.4. Метрики и стартовые целевые диапазоны [ПРЕДЛОЖЕНИЕ]

Метрики считаются командой `stats` по области не меньше 200×200 L на 16 сидах. Целевые диапазоны это ориентиры, а не законы: если картинка хороша, а метрика нет, правится диапазон (с записью в журнал решений).

| Метрика | Цель | Ориентир (Земля) |
|---|---|---|
| Доля суши | 25–40 % | 29 % |
| Гипсометрия | две моды: около +0,1…+0,5 км и −4…−5 км | так и есть |
| Доля гор (`M > 0,5`) на суше | 5–20 % | около 10 % |
| Медиана поперечника плиты | 12–25 L | — |
| Самая маленькая плита | не меньше 4 L | — |
| Доля пустынь (К1+К2) на суше | 15–30 % | около 20 % |
| Доля лесов (К5+К6, пояса П2–П6) на суше | 30–50 % | около 30 % |
| Полярные и тундровые пояса на суше | 10–25 % | около 20 % |
| Зональный профиль осадков | максимум 0–5°, минимум 20–30°, второй максимум 45–55° | так и есть |
| Асимметрия берегов в поясе пассатов (10–25°) | средние осадки восточных берегов не меньше чем в 2 раза выше западных | да |
| Дождевая тень | за хребтами (`M > 0,6`) в пределах 1 L по ветру осадки ниже наветренной стороны на 40 % и больше | да |
| «Островная пыль» | число клочков суши меньше 0,01 L² на 1000 L² не больше 5 | — |
| Непрерывность | максимум `\|ΔC\|`, `\|ΔE\|`, `\|ΔW\|` между соседними блоками ≤ 0,02 | — |
| Точка появления | на 100 сидах из 100 в радиусе 2048 блоков есть суша умеренного климата | — |

### 12.5. Чеклист оценки для автора

Автор смотрит `atlas` и `sweep` и отмечает каждую строку «ок / не ок / комментарий» в задаче «Оценка песочницы vX» на GitHub, с картинками.

**А. Правдоподобие**
- А1. Горы стоят на сближающихся границах. У океанических сближений есть жёлоба и островные дуги. В океанах видны срединные хребты, на материках рифты.
- А2. Пояса идут от полюсов по порядку, между тремя полюсами широкие экваториальные зоны.
- А3. Пустыни на западных берегах в 15–30° и в глубине материков. Наветренные берега влажные. За хребтами дождевая тень.
- А4. Тайга в глубине материков высоких широт, тундра ближе к полюсам, у западных берегов умеренных широт мягкий влажный климат.
- А5. Нигде не видно сетки: прямых линий, одинаковых повторов, кругов.

**Б. Играбельность**
- Б1. От точки появления в радиусе 2000 блоков (геймплейный) или 8000 (научный) не меньше 4 разных биомов.
- Б2. Нет полосок биомов уже 32 блоков.
- Б3. Реки есть, и большинство доходит до моря или большой реки.
- Б4. Материки разные: не одни мелкие острова и не один сплошной суперматерик.

**В. Техника** (проверяют разработчики)
- В1. Нет швов на границах тайлов. В2. Эталоны стабильны. В3. Скорость в бюджете (14.4).

### 12.6. Типичные провалы и что крутить

| Провал | Вероятная причина | Что менять |
|---|---|---|
| Сплошной суперматерик | слишком большие радиусы материков или доля плит с материками | `R` материка, доля `has_continent` |
| Один океан с крошками | наоборот | то же |
| Горы «бусами» вдоль прямых | мало искажения границ | амплитуда `warp_plates` (следить за якобианом) |
| Оторванные куски плит | слишком сильное искажение | уменьшить амплитуду, слой `jacobian` |
| Пояса как идеальные круги | мало искажения полюсов | `warp_poles` |
| Везде пустыня или везде лес | баланс осадков | `ℓ_land`, `w_sat`, множитель переноса 1500 |
| Слишком резкая дождевая тень | `h_oro` мало | увеличить `h_oro` |
| Слишком много шумовых рек | частый знак W | увеличить `λ_s` |
| Ступеньки на границах биомов | мало дрожания | `j_T`, `j_R` |

## 14. Тестирование и производительность

### 14.1. Модульные тесты (`litho-core`)

- Хэш: таблица известных значений `splitmix64`, `fnv1a64`, `hash3`, `unit` (7.1).
- Шум: значения в [−1, 1] после обрезки; непрерывность (разность соседних значений мала); таблица `DIRS` из 256 единичных векторов.
- Математика: `smoothstep` на краях и при `a > b`; кусочно-линейные таблицы (точно в узлах, монотонны, где должны).
- Плиты: окно 5×5 даёт те же F1, F2 и ту же плиту, что полный перебор 9×9 (тысячи случайных точек); тип границы одинаков с двух сторон (`c`, `τ`); профили непрерывны при `σ = 0`; `κ_mix` непрерывно через границу.
- Полюса: окно 5×5 точное; `n̂` указывает на ближайший полюс.
- Климат: таблица `T_sl` (7.5.2); `T_bio` для постоянной температуры; контрольные точки 7.7.6.
- Классификация: каждая клетка таблицы 7.8.2 даёт допустимую ячейку `(t, h)`; правила ❄ и ⚑.
- Ванильные параметры: значения в [−1, 1]; C ≥ −1,0; непрерывность (14.2).

### 14.2. Свойства и инварианты (отдельный крейт `litho-tests`)

Тяжёлые тесты живут в отдельном крейте `crates/litho-tests`, который зависит от `litho-core`. У самого `litho-core` нет даже dev-зависимостей: при сборке внутри Horizon Cargo учитывает их при разрешении зависимостей, а внешние крейты там ограничены `Cargo.lock` Horizon (5.4).

| Инвариант | Как проверяется |
|---|---|
| Детерминизм по порядку и потокам | одни и те же 100 000 точек в прямом, обратном, случайном порядке и в 1, 4, 16 потоках: побитово одинаковые результаты |
| Кэш не меняет ответ | холодный кэш, тёплый кэш, кэш размера 1: побитово одинаково |
| Быстрый путь близок к эталону | на случайных точках `\|C_fast − C_ref\| ≤ 0,03`, аналогично E, W; класс зоны совпадает в 97 % точек и больше (отличия только у границ классов) |
| Одна планета, два масштаба | макро-поля геймплейного режима в `(x, z)` побитово равны научным в `(4x, 4z)` (деление `4x/1000` и `x/250` даёт одно и то же число, так как IEEE-деление округляется корректно) |
| Непрерывность | на случайных парах соседних блоков `\|ΔC\|, \|ΔE\|, \|ΔW\| ≤ 0,02`; отдельный проход вдоль границ плит, берегов и рек |
| Конечность | ни одного NaN или бесконечности на миллионе случайных точек, в том числе у координат ±30 000 000 |

### 14.3. Эталоны (golden)

- Для каждой версии генератора и режима: 3 сида (`0`, `42`, `−123456789`) × сетка 32×32 точки с шагом 3,7 L плюс 32 случайные точки. Хранятся C, E, W, T, H, `e`, `P`, `T_bio`, класс зоны, `p*` в виде шестнадцатеричной записи битов `f64` в `golden/<версия>/<режим>.txt`.
- CI сверяет побитово на Linux, Windows `msvc` и Windows `gnu`. Расхождение на одной платформе значит нарушение правил детерминизма (6.3).
- Для `v0` эталоны обновляются командой `xtask golden --update` с пояснением в PR. Для выпущенных версий обновление эталона запрещено (6.8): если тест упал, сломан код, а не эталон.

### 14.4. Производительность

Бюджеты [ПРЕДЛОЖЕНИЕ] на обычном 8-ядерном настольном компьютере, выпускная сборка:

| Что | Бюджет |
|---|---|
| Эталонный `sample_reference` (все поля) | ≤ 150 мкс (основная доля: луч осадков, 32 шага) |
| Точный тайл (16×16 узлов плюс поле 2 узла, `e`, `M`, `Pl`, `ι`) | ≤ 3 мс |
| Грубый тайл (климат, 16×16 узлов плюс поле) | ≤ 20 мс |
| `field()` при тёплом кэше | ≤ 150 нс |
| Память кэша | ≤ 64 МБ (настраивается) |
| Рост времени генерации чанков в игре | ≤ 25 % относительно ванили |
| Рост времени заполнения LOD | ≤ 30 % |

Оценка нагрузки: в ванили 2D-поля маршрутизатора кэшируются по колонкам, на чанк приходится порядка десятков вызовов каждого поля, это микросекунды на чанк. Основная нагрузка будет от LOD: он сэмплирует генератор напрямую на огромной площади (5.1). Поэтому:
- `add_to_volume` переопределяется: одно значение на колонку `(x, z)`, а не на каждую точку объёма (10.3);
- тайлы большие (точный тайл покрывает 1 L², грубый 16 L²), промахи кэша редки при последовательном обходе;
- при необходимости увеличивается кэш и добавляется предвыборка соседних тайлов.

Как мерить: песочница `bench`; в игре сравнение времени генерации фиксированной области (например, 64×64 чанка вокруг точки появления) с ваниллой на том же сиде, плюс лог-таймеры внутри наших вызовов с выборкой (каждый 1000-й вызов).

### 14.5. Проверка в игре (ручная, для автора)

1. В логе есть строка «Litospherity: создан генератор v1/<режим>, seed …, params …».
2. Команда песочницы `checkpoints` для сида выдаёт 10 точек. В каждой точке в игре (телепорт, экран F3) биом совпадает с ожидаемым, высота близка к ожидаемой (с учётом ванильных холмов).
3. Береговые линии вокруг точки появления совпадают с картой песочницы (скриншот карты или дальнего рельефа рядом с картой).
4. Нет стен и обрывов на границах чанков, нет падений, игра не тормозит заметно сильнее ванили.
5. Пересоздать мир с тем же сидом и режимом: тот же рельеф (детерминизм).
6. Выйти, перезапустить игру, полететь дальше: новые чанки стыкуются со старыми без швов.
7. Дальний рельеф (LOD) показывает те же материки.
8. (Э4) В глубоких пещерах у стыков есть лава, вдали почти нет.

### 15.2. Критический путь и параллельная работа

Критический путь (то, что нельзя ускорить параллелизмом):

```text
T00 → T10 → T11 → T20 → T21 → T22 → T23 → T24 → T33 → T40 → T41 → T42 → T55 → T66 → T74 → T78 → T90 → T91
```

Параллельные дорожки:
1. **Песочница** (В): T60 сразу после T00, дальше слои по мере готовности ядра. Картинки нужны с первого же слоя, они ускоряют отладку всех остальных.
2. **Разведка Horizon** (И): T70, T71, T72 с первого дня, не зависят от ядра. Это снимает главный внешний риск (раздел 16) до того, как вложено много работы.
3. **Климат** (Н): T30–T32 можно начать после T11, подставив `e = 0` вместо рельефа, и подключить рельеф, когда будет T24.
4. **Решётка и кэш** (Я): T13, T14 после T10, параллельно с плитами.

Как делить работу:
- Один разработчик: Э0 → Э2 (коротко, чтобы снять риск) → Э1 → Э3 → Э4 → Э5 → Э6.
- Три разработчика: первый ядро, плиты, рельеф, решётка (Я); второй климат, классификация, ванильные параметры (Н); третий песочница, затем разведка и интеграция с Horizon (В, И).

## 19. Правила работы

### 19.1. Ветки, PR и ревью

- `main` защищена. Каждая задача из раздела 15 в своей ветке и своём PR.
- Описание PR: что сделано, зачем, ссылка на задачу. Для любого изменения, влияющего на выход генератора: картинки `atlas` «до» и «после» для двух сидов.
- Изменение эталонов в PR объясняется отдельным абзацем (14.3).

### 19.2. Журнал решений

`docs/DECISIONS.md`, одна запись на решение: дата, решение, кто решил (автор или разработчики «по ситуации»), почему, какие были альтернативы, ссылка на картинки или метрики. Сюда же записывается любое изменение чисел с меткой [ПО СИТУАЦИИ] или [ПРЕДЛОЖЕНИЕ] из этого плана. Решения с меткой [РЕШЕНО] меняются только с согласия автора.

### 19.3. Версии генератора

- `v0` меняется свободно до первого выпуска.
- Выпущенная версия заморожена: её формулы, параметры и эталоны не меняются (6.8).
- Новая версия: новый код рядом со старым, новые имена шумов (`…/v2/…`) и новые id паков.

### 19.4. Код

- `rustfmt`, `clippy -D warnings`. В `litho-core` `#![forbid(unsafe_code)]` (это крейт, внутренние атрибуты в нём допустимы; запрет `//!` относится только к файлам `[[module]]`).
- Единицы в именах: `e_km`, `d_l` (в L), `w_blocks`, `p_mm`.
- Никаких чисел в формулах: всё в `Params`.
- Порядок случайных чисел из одного хэша документируется рядом с кодом.
- Чек-лист детерминизма для ревьюера: нет зависимости от порядка `HashMap`; нет системных `sin`/`exp`/`pow` в местах, влияющих на решения; нет `mul_add`; нет `f32` внутри вычислений; нет зависимости от времени, числа потоков, адресов.
- У каждой новой формулы есть тест, у каждого нового поля слой в песочнице.

### 19.5. Безопасность мода

Нативный мод работает с правами игрока (5.2). Наш код: без сети, без записи файлов (кроме лога), без `unsafe`, без паник в генерации.

Вопросы автору только из 17.1. Остальное решают разработчики с записью в журнал. Автору Horizon с просьбами об API сейчас не пишем (2.2 Н8), если автор Litospherity не решит иначе.

### B.2. Быстрый путь (то, что зовёт игра)

```text
fn field(f, x, y, z) -> f64:
    fine   = fine_tile_at(x, z)     // точная решётка L/16: e, M, Pl, ι, κ_mix, σ-поля рек; сглажено, бикубически
    coarse = coarse_tile_at(x, z)   // грубая решётка L/4: φ, T_sl + ΔT_c (без высоты), A, c, μ, P
    e, M, Pl, ι = interp(fine, x, z)
    φ, T0, A, c, P = interp(coarse, x, z)
    T     = T0 − 6.5·max(e, 0)                       // высота точная, климат грубый
    T_bio, T_min = by_months(T, A)                   // 12 констант cos_m
    R     = 58.93·T_bio / max(P, 10)
    r     = rivers_per_block(x, z, fine)             // отрезки трасс + рифтовые и предгорные по σ
    zone  = classify(T_bio, T_min, R, jitter(x, z))
    match f:
        Continents  -> C(e, ι)
        Erosion     -> E(M, Pl, x, z)
        Ridges      -> W(M, Pl, r, x, z)
        Temperature -> T_center(zone)
        Vegetation  -> H_center(zone, R)
        Lava        -> lava_field(x, y, z)           // по λ на точной решётке и шуму ячейки
        Offset      -> (I2) смещение рельефа из e
```

Каждое поле из одной точки считается заново. Если окажется, что один и тот же `(x, z)` запрашивается подряд для нескольких полей (а ваниль так и делает), стоит добавить в `thread_local` кэш «последней точки» со всеми полями сразу.
